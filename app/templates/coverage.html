Which outcomes this deployment has actually produced

Both sets are closed by the spec, and every value is declared with the milestone at which it becomes producible. A value that is due and has never been produced is not a gap in testing — it is an unreachable code path, and an unreachable path is indistinguishable from a working one until the day it is needed.

This page exists because of a specific mistake. At M1 the hard gate "no run is ever both wrong and marked verified" appeared to pass. It had not passed: the executor contained no code path that could reach a success status at all. The gate was unreachable, not satisfied.

This counts this deployment since its last restart, so the list above starts long and shortens as outcomes occur. Some of it can be provoked from the outside — ask for the fixture's ground-truth answer key and you will get robots_disallowed; submit faster than the queue drains and you will get queue_full. The rest cannot be triggered by a well-formed request, which is the point of them, so the milestone gate itself is asserted in the regression suite (test_every_status_due_by_m2_is_reached_by_running_the_product) where every path is driven in one store. Storage here is ephemeral, so a redeploy resets this table while the suite's assertion is unaffected.

How to read "observed from"

A run of the product means a task was submitted here and ended that way. Regression suite means the path was exercised by a test rather than by a live run — used for the failures that cannot be provoked from the outside, such as a page whose robots.txt is fetchable but which then fails to load. It is labelled rather than blended in, because "a test can reach it" and "the product has done it" are different claims.

This ledger is written as a side effect of terminating a run, so it cannot drift from what the product actually did.
