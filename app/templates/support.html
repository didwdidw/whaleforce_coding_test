Limitations of the design itself

  • This build is {{ build.milestone }}. A model plans; it does not judge. Every status still comes from deterministic re-extraction against the stored artifact, and the executor cannot set a success status itself. {% if not build.locator_memory %}Locator memory is not in this build. {% else %}Locator memory is present and deliberately small: written back only from verified runs, re-resolved and re-verified on use, quarantined after three consecutive failures. It is a hint that saves search effort, never a proof.{% endif %}
  • Each promised record is reachable two ways — planned by the model, which is {% if build.planner_is_default %}what a plain-language task gets by default{% else %}not currently the default{% endif %}, and by a scripted plan that needs no provider quota. The scripted path is what the pinned demonstrations run on, so the frontend stays inspectable when the provider is not reachable, and it is the baseline the analysis report compares against. Both go through the same verification, and each run records which one it took.
    • {% if build.generic_loop %}
  • An experimental run is held to a weaker postcondition, and the difference matters. The site and the binding rule are frozen before browsing, but the label cannot be — nobody knows it in advance on a site we have never seen. So the model points at where a value lives and names the label it is bound to; code reads the value from that label, first on the live page and again from the stored artifact. That is one rule over two captures, where a promised record gets two independent rules. It catches a value not bound to its label and a page that changed under the run. It would not catch the rule itself being wrong.
    • {% endif %}
  • verified does not mean "true". It means the claim is consistent with a preserved artifact and passes deterministic type, unit, date and entity checks. A value that is correct in form but taken from the wrong row, entity or period can still pass; label→value structural binding narrows this without closing it.
  • A moved label costs a claim, deliberately. When the label a value is bound to changes, the value may still be on the page and readable by other means — the run is downgraded to partial anyway, because a binding that cannot be made is not a verification. Re-anchoring is a recovery behaviour and is in this build.
  • A quiet outcome can hide a defect. An abstention, a proven absence and a refusal all look like caution from outside. Runs are audited for the conditions that make a quiet outcome untrustworthy — chiefly, having refused on a reduced view that dropped something the goal named — and one that trips the audit is shown as not a clean outcome rather than as a clean one. It only covers what we thought to look for.
  • Necessary UI actions are declared, not proven. The harness verifies that a case declared an action as required and the trace shows it happened. It does not prove the action was impossible to bypass. Only the fixture's GS-1/GS-2/GS-3 are shortcut-proof by construction.
  • Injection is mitigated structurally, not prevented. Goal, postcondition and policy live outside model-mutable state, the executor accepts a fixed action allow-list, and navigation is checked against an origin policy. Page content still necessarily influences the next action.
  • DNS rebinding is not solved. Addresses are checked at resolve time and the connection is not pinned to them.

Site policy

books.toscrape.com was chosen because its automation policy is unambiguous — it is a public sandbox built for automation practice and serves no robots.txt at all. arXiv was dropped because its robots policy forbids the operations we needed: Crawl-delay: 15, Disallow: /search, /find, /form, /api, and a stated policy that indiscriminate automated downloads are not permitted. Neither choice is a research narrative.

Per-origin pacing is our own voluntary limit, not compliance with a robots directive. Wikipedia's Crawl-delay: 5 applies to a named bot, not to User-agent: *, so no crawl-delay is imposed on us there. SEC EDGAR is self-limited to 1 request/second against their published cap of 10, with a declared contact User-Agent — which their server requires, not merely requests.
