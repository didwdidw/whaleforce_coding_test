## 0. 一句話總結

**這個系統的賣點不是「答對率高」，而是「它不會在答錯的時候說自己答對了」。**
為了做到這件事，我們付出的代價是承諾的表面很小（四筆記錄）、拒絕率很高、
而且 held-out 測試只拿到 1/8 —— 而那個 1/8 本身，是這份提交裡資訊量最高的一筆資料。

## 1. 最終版系統

### 1.1 這個系統怎麼運作

**核心是一句話：模型只負責「提議」，決定性的程式碼負責「裁決」，而裁決的對象是儲存下來的位元組，不是即時的網頁。**

一般的瀏覽器 agent 失敗的方式都一樣：模型看了頁面，說「答案是 42」，系統就回報 42。
如果模型看錯了，整條流程裡沒有任何一個環節能發現。這叫 **silent failure（安靜的失敗）**，
是最傷使用者的一種——因為使用者沒有理由懷疑它。這整個系統就是為了防這件事而設計的。

具體的三段式：

**第一段，開瀏覽器之前。** 任務會被編譯成一個 **postcondition（後置條件）**——
「要回答這個任務，必須成立哪些主張、必須真的發生哪些 UI 動作」。
它會被 SHA-256 雜湊並凍結，後面任何環節都不能改它。

這一步為什麼重要：如果「什麼算成功」是看完頁面之後才決定的，那 agent 永遠可以說服自己已經成功了。
凍結它的代價是——有時候 run 會因為「我們問錯問題」而失敗，而那個失敗會被看見，不會被吸收掉。

**第二段，瀏覽的時候。** 每一個重要的頁面狀態都會被存成 artifact（完整 DOM ＋ 文字 ＋ 截圖），
以 SHA-256 內容定址。導航步驟另外記三件事：計畫的目標 URL、完整的重導向鏈（含每一跳的狀態碼）、
以及回應的最終 URL。

**第三段，瀏覽之後。** 模型提出一個答案——**這個答案被當成假設，不是結論**。
決定性的 verifier 會重新打開儲存的 artifact，試著在裡面重新定位那個值，
而且必須是**結構上綁定在任務所指名的 label 上**（例如「UPC」這個表頭底下的那一格，
不是頁面上任何一個長得像 UPC 的字串）。
**如果在儲存的位元組裡重新解析不出來，這個 run 就不算成功，不管模型多有信心。**

為什麼要用儲存的位元組而不是即時頁面：即時頁面可能在「答案產生」跟「檢查」之間變了，
那樣檢查通過跟答案正確就是兩件不相干的事。儲存的位元組不會變，
而且任何人（包含評分者）拿著 `/api/artifacts/{id}` 都能自己重做一次同樣的驗證。

**兩個因此付出的代價，值得直接講：**

- **「不存在」永遠不用推論的。** 「我找了但沒找到」不是「沒有」的證明。
  要回報 `no_result_verified`，必須有一個定位到的 empty-state 元素，
  或是一個能證明整個結果集都被讀過的覆蓋錨點。否則就棄權。
- **用錯的方法拿到對的答案，算失敗。** 如果案例宣告「必須送出表單」，
  而 run 用猜結果頁 URL 的方式拿到正確的值，一樣判 fail。
  用捷徑通過的 agent 沒有展示它宣稱的能力。

**另外兩個機制**（作業明確要求的自我修正與自我維護）：

- **自我修正**：系統嚴格區分 *retry*（同一個策略家族再試一次，這不算自我修正）
  跟 *recovery*（換到不同的策略家族，而且必須帶一個從封閉集合裡挑出來的**具名診斷原因**）。
  策略家族有六個：F1 語意/無障礙樹、F2 文字標籤、F3 結構、F4 視覺座標、F5 替代路徑、F6 替代表示。
  「這一步丟了例外」不算診斷，不會被接受。
  **F4（用截圖座標亂點）在 planner 邊界就被拒絕**——盲點正是這個產品要防的失敗。
- **自我維護**：locator memory，key 是 `(origin, operation, role)`。
  只有 `succeeded_verified` 的 run 會寫回——**不是「點得動就記住」**，
  因為一個點得動但答案沒人能重新解析的 locator，正是我們最不想重用的那一個。
  記住的東西是「元素的身分」，永遠不是「值」；而且記住的 locator 一樣要重新解析、重新驗證，
  它只省搜尋成本，不省證明。14 天確認窗、連續三次失敗就隔離。

### 1.2 使用者會遇到什麼限制

**最重要的一句：這個系統對可靠度的承諾是「以 `site × operation` 記錄為單位」，不是以網站為單位。**
會在 Wikipedia 排序表格，不代表會在 Wikipedia 展開 navbox；那是兩筆不同的記錄、要各自的證據。

| 分層 | 意義 | 算不算進頭條成功率 |
|---|---|---|
| **T-DECLARED** | 命中下面四筆承諾記錄 | **算** |
| **T-EXPERIMENTAL** | 其他公開、政策乾淨、唯讀的站。盡力而為，**棄權是正確結果** | 不算，另外報 |
| **T-REFUSED** | 違反政策，瀏覽前就拒絕 | 不適用 |

分層是在**執行前**決定的，而且會顯示在表單、結果與 API 回應上。

**承諾的四筆記錄**（fixture 上原本那三筆已經退出承諾——在自己寫的網站上量成功率，等於自己出考卷自己改）：

| ID | 站 | 操作 |
|---|---|---|
| OP-4 | en.wikipedia.org | 依指定欄位排序 wikitable，讀新的第一列的某一格 |
| OP-5 | en.wikipedia.org | 展開收合的區塊／navbox，讀一個展開前看不到的值 |
| OP-6 | books.toscrape.com | 走分類、翻頁、擷取清單層級的事實 |
| OP-7 | books.toscrape.com | 開商品詳情頁，擷取一個**有標籤的**欄位（UPC、Availability、Price excl. tax） |

**使用者會實際撞到的限制，按撞到的機率排：**

1. **必須指名起點。** 任務要指名網站或頁面。
   「Wikipedia 上那個 S&P 500 成分股表格」不會解析成單一頁面標題，
   而「去搜尋然後挑一個結果」等於自己選了一個任務沒指定的起點——那是在回答沒人問的問題。
   這條在 held-out 測試裡吃掉了 8 題中的 2 題。
2. **承諾的路由認得的措辭，比 support matrix 承諾的窄。**
   held-out 的四題 declared 案例，有兩題被路由成 T-EXPERIMENTAL，根本沒碰到承諾表面。
   我們自己的 dev split 量不到這件事，因為那些案例是「已經知道 router 吃什麼的人」寫的。
3. **只支援英文任務。** 中文與其他語言最多走到 experimental。
   這是明說的限制，不是疏漏——沒評估過的承諾不是承諾。
4. **唯讀。** 不送出表單（fixture 除外）、不登入、不寫入。
5. **robots.txt 是強制執行的，不是參考的。** RFC 9309 語意。
   被禁的路徑回 `blocked / robots_disallowed`，並引用匹配到的規則。
   Wikipedia 禁 `/wiki/Special:Search`，所以「用 Wikipedia 搜尋頁找 XXX」這種很正常的問題，在這裡沒有答案。
   **而且：抓不到 robots.txt 時也會拒絕**（fail-closed），這一點在 §3 會再講，它咬過我們一次。
6. **多頁的「不存在」證明不了。** 跨好幾頁的分類會跨好幾個 artifact，而這個版本只對一個 artifact 驗證。
   單頁分類會回答；多頁的會回 `unverified` 並說覆蓋率未證明，而不是拿看到的那一頁當全部。
7. **步數預算是 fail-closed 的。** 每個 run 有步數與 token 預算，用完就 `budget_exhausted`、沒有答案，
   而不是把「剛好走到的那一頁」當成最後一頁回報。
8. **並行度 2，佇列深度 2。** 第五個同時進來的請求會拿到 `blocked / queue_full` 加 `Retry-After`——
   這是設計好的狀態，不是錯誤頁。記憶體是這台機器的瓶頸（峰值 2,320 MB / 4 GB），並行度 2 是量出來的，不是猜的。

## 2. 使用者操作流程與後端機制

**一句話：從按下送出到看到結果，中間有 13 個步驟，其中模型只參與 2 個，而且那 2 個的產出都要再被程式碼審一次。**

下面按順序走一遍。每一步回答四件事：做什麼、誰在服務、怎麼被驗證、產出什麼。

### 步驟 1 — 收件與排隊

- **做什麼**：接受 `POST /api/runs`（表單或 JSON），配一個 run id，進佇列。
- **誰在服務**：`app/server.py` + `app/queue.py`。**純程式碼，沒有模型。**
- **怎麼驗證**：容量檢查。並行度 2、深度 2，超過就回 `blocked / queue_full` 加 `Retry-After`，
  在 API、run 頁面、健康端點三個地方讀起來都是終局狀態。不會有請求被默默丟掉或吊著等逾時。
- **產出**：run id、`queued` 狀態、一條 SSE 進度串流的位址。

### 步驟 2 — 分層判定（tier）

- **做什麼**：判斷這個任務是 T-DECLARED / T-EXPERIMENTAL / T-REFUSED。
- **誰在服務**：`app/records.py`。**純程式碼**，比對承諾記錄清單。
- **怎麼驗證**：**在執行之前**決定，並且寫進 run 紀錄；表單、結果、API 三處都看得到。
  執行後不能改——不然「宣告層成功率」這個數字可以事後被挑出來。
- **產出**：一個分層標籤，以及（若是 T-REFUSED）一個瀏覽前的終止。

> **這一步是 held-out 測試打得最痛的地方**：8 題裡有 3 題的分層跟出題者的宣告不一致，
> 而且方向是壞的（該 declared 的變成 experimental）。詳見 §3。

### 步驟 3 — 編譯並凍結 postcondition

- **做什麼**：把自然語言任務編譯成結構化的後置條件：目標 URL、任務自己指名的站（`named_site`）、
  凍結的輸入參數、必須發生的 UI 動作、以及每一個「主張」要透過哪個 label 與哪種結構關係去驗證。
- **誰在服務**：`app/postcondition.py`。**純程式碼**（模型不參與這一步）。
- **怎麼驗證**：整個物件被正規化序列化後取 SHA-256 並記錄。
  驗證階段會用 `matches_frozen()` 重算一次——**雜湊不一致本身就是失敗**，
  因為那代表「拿去驗證的物件」不是「run 當初承諾的那個物件」。
- **產出**：一個凍結且雜湊過的 postcondition。

  凍結兩樣容易被當成實作細節、但其實是機制核心的東西：
  **凍結輸入**（搜尋的詞、排序的欄位與方向）——驗證時會去讀頁面自己回顯的詞來比對，
  一個「搜了別的東西」的 run 會產生一個完全合法的頁面，除了這個比對沒有東西擋得住它；
  **凍結錨點**（label 文字與結構關係）——在知道答案之前就選好，
  不然 verifier 最後只會確認 executor 本來就相信的東西。

### 步驟 4 — 政策閘門（robots + egress）

- **做什麼**：檢查 robots.txt 是否允許；解析目標 IP 並擋掉內網／loopback。
- **誰在服務**：`app/robots.py`（RFC 9309 實作，有專屬 CI job）＋ `app/egress.py`。**純程式碼。**
- **怎麼驗證**：**每一次導航、每一跳重導向都重新解析並重新檢查目標 IP**——
  loopback、RFC 1918、link-local `169.254.169.254`、IPv4-mapped private、CGNAT、非 http scheme 全擋，
  測試在 `tests/test_policy.py`。另外，production 環境若偵測到 egress guard 被關掉，**直接拒絕啟動**。
  每個 run 的 trace 都會記錄當下 guard 是不是開的——稽核看得到，不用相信我們的說法。
- **產出**：允許通過，或 `blocked / robots_disallowed`（附上匹配到的規則）／IP 拒絕。

### 步驟 5 — 規劃（模型第一次登場）

- **做什麼**：模型看一個**縮減過的**頁面視圖，提議**一個**下一步動作。
- **誰在服務**：`app/planner.py` + `app/provider.py`（模型：`gemini-3.1-flash-lite`，固定版本，
  不用 `latest` 或 preview 別名——會動的模型會讓所有先前的量測都在描述一個不存在的系統）。
  頁面縮減在 `app/reduce.py`。
- **怎麼驗證**：**回來的東西一律當提議，執行前先驗**：
  動作必須在 8 個允許動作的白名單內（click / fill / select / press / wait_for / extract / finish / abstain）；
  `ref` 必須真的存在於我們送出去的那個視圖裡（**模型自己發明的 ref 會被拒絕**）；
  診斷原因必須是封閉集合裡的具名原因。驗不過的提議會被記錄並拒絕，**不會被「修成看起來合理的樣子」**。
- **產出**：一個通過驗證的動作，或一個被記錄的拒絕。

  這裡也是 prompt injection 的防線，而且它是**結構性的**，不是靠關鍵字過濾：
  模型本來就沒有能力去改目標、分層、政策、預算或記憶——那些都活在程式碼裡，
  頁面文字寫不到那些地方。locator memory 也只餵給 locator 解析，不會以自由文字注入 planner。

### 步驟 6 — 瀏覽與 artifact 擷取

- **做什麼**：真的用 Chromium 執行那個動作，然後把頁面狀態存下來。
- **誰在服務**：`app/executor.py` + `app/browser.py` + `app/store.py`。**純程式碼。**
- **怎麼驗證**：artifact 以內容定址（SHA-256）；導航步驟同時記錄
  計畫目標 URL、完整重導向鏈（每一跳含狀態碼）、回應最終 URL、導航當下的 `page.url`、
  以及文件自己宣告的 `rel=canonical`。
  **五個值全部記下來、不化簡成一個**——化簡成一個，正是讓一個「兩者不一致時」的檢查變成擲骰子的做法。
- **產出**：一組 artifact（完整 DOM ＋ 文字 ＋ 截圖）與一條完整的 trace。

### 步驟 7 — 模型提出答案

- **做什麼**：模型說「答案是 X」。
- **誰在服務**：`app/planner.py` / `app/provider.py`。**模型第二次也是最後一次登場。**
- **怎麼驗證**：**這一步完全不驗，因為它不是結論。** 它是假設，往下送。
- **產出**：一個候選值 ＋ 一個 label 錨點。

### 步驟 8 — 決定性驗證（整個產品的核心）

- **做什麼**：重新打開**儲存的 artifact**，在裡面重新定位模型宣稱的值。
- **誰在服務**：`app/verifier.py`。**純程式碼，模型完全不參與。**
- **怎麼驗證**：值必須從任務指名的 label 出發、透過 postcondition 在**凍結時就選好**的結構關係到達。
  關係是封閉集合，例如：`table_row_cell`（表頭在同列，值在資料格）、
  `table_column_cell`（欄位標題在上，值在下）、`counter_echo`（`N results for "term"` 這種回顯句）、
  `pager_position`、`list_enumeration`、`empty_state`、`element_absent`、`sort_state` 等。
  **「頁面上某處出現過這個字串」不算答案。**
- **產出**：每個主張的 verified / 未 verified，以及它是從哪個 artifact id ＋ SHA-256 重新擷取出來的。

### 步驟 9 — 兩道 artifact 來源閘門（Amendment 26）

- **做什麼**：確認「拿來驗證的位元組」真的來自「計畫要去的那一頁」。
- **誰在服務**：`app/verifier.py`。**純程式碼。**
- **怎麼驗證**：**拆成兩條可以各自單獨失敗的斷言**：
  1. `artifact_source_is_accounted_for_by_the_trace`——這批位元組來自 trace 交代得出的某一頁。
  2. `landing_explained_from_the_plan_target`——那一頁是從計畫目標經過**有紀錄的路線**到達的：
     它本身就是目標、或是一條**從目標出發**的重導向鏈的終點（鏈的第一跳必須是目標、
     最後一跳必須是來源、最後一跳以外每一跳都必須是 3xx）、
     或是目標頁自己宣告的 `rel=canonical`（**限同源**）。
- **產出**：通過，或 `failed / verification_mismatch` 並說明哪一條斷言不成立。

  fixture 為這兩條各準備了一個負向案例。最重要的是 `/detour`：它 301 到**跟 `/moved` 完全相同的頁面**。
  只比對最終 URL 會通過——但「一個本該從 `/moved` 出發的 run 是怎麼到那裡的」沒有交代，
  而「用沒交代的路線抵達正確答案」在這個系統裡就是失敗。

### 步驟 10 — 安靜結果的稽核

- **做什麼**：對「安靜的結果」（棄權、宣稱不存在、被擋）額外做一次稽核。
- **誰在服務**：`app/suspicion.py`。**純程式碼。**
- **怎麼驗證**：把這類結果跟**縮減記錄**對照。
  一個因為「我們自己的頁面縮減把元素砍掉了」而產生的棄權，
  跟一個誠實的棄權從外面看**一模一樣**——所以每個安靜結果都要對照 reducer 砍了什麼，對得上就掛徽章。
- **產出**：一個或多個「這個安靜結果不該被當成乾淨資訊」的理由。
  **這一步不會改變任何狀態**——它不能讓 run 通過，也不會把 run 降級，它只附上讀者需要的東西。

### 步驟 11 — 終局狀態

- **做什麼**：從兩個封閉集合各挑一個標籤收尾。
- **誰在服務**：`app/models.py` 定義集合，`app/executor.py` 收尾。**純程式碼。**
- **怎麼驗證**：**7 種 `terminal_status` × 18 種 `failure_class`，兩個都是封閉集合，只能靠書面修訂擴充。**
  `partial` 和 `unverified` 在產品的任何地方都不會被渲染、聚合或描述成成功——
  這個保證之所以有意義，正是因為集合是封閉的、規則是機械的。

  | terminal_status | 意思 |
  |---|---|
  | `succeeded_verified` | 有答案，而且在儲存的位元組裡重新解析出來了 |
  | `no_result_verified` | 證明了「沒有」——要有 empty-state 元素或覆蓋錨點 |
  | `partial` | 任務問了 n 件事，只驗證出其中幾件 |
  | `unverified` | 有東西，但證不出來 |
  | `failed` | 沒做到 |
  | `blocked` | 有東西擋住（robots、佇列、配額、執行中遇到的障礙） |
  | `unsupported` | 我們不做這種事，或這頁給不出可綁定的 label |

### 步驟 12 — 前端呈現與 evidence bundle

- **做什麼**：把結果、完整 trace、artifact 攤開給人看。
- **誰在服務**：`app/server.py` + `app/evidence.py` + `app/coverage.py`。
- **怎麼驗證**：`/runs/{id}` 顯示每一步、每個檢查的通過與否、每個互動是
  *from memory* / *healed* / *freshly derived*；`/api/artifacts/{id}` 讓任何人重做驗證；
  `/support` 是支援矩陣與已知限制；`/coverage` 是證據覆蓋；`/healthz` 是運作狀態。
- **產出**：一個可檢視的 run 頁面，以及一份可下載的 evidence bundle。

### 步驟 13 — 寫回 locator memory

- **做什麼**：把這次用到的元素身分記起來。
- **誰在服務**：`app/memory.py`。**純程式碼。**
- **怎麼驗證**：**只有 `succeeded_verified` 的 run 會寫回**。14 天確認窗，過期算 stale；
  連續三次失敗就隔離並記錄理由。計數器在 `/healthz` 上。
- **產出**：一列 `(origin, operation, role) → 元素身分`。**永遠不存值。**

### 這條流程的重點，用一句話收

**模型只出現在步驟 5 和步驟 7，而且兩次的產出都要再被程式碼審一次：
步驟 5 的動作提議會被白名單與 ref 存在性擋下，步驟 7 的答案會被步驟 8–9 用儲存的位元組推翻。
其餘 11 個步驟完全沒有模型。**

## 3. 開發過程遇到的困難與對應修改

**這一節是這份報告的重點。**
所有困難裡最重要的一族，我們自己給它取了名字：**「一個回報巧合的檢查」**。
到目前為止找到 **10 筆**，修好 **7 筆**，剩下 3 筆是凍結之後才發現的、明說不修並寫明理由。

下面每一筆都是「困難 → 為什麼難 → 怎麼改 → 代價」。

---

### 3.1 反覆出現的缺陷族：一個回報巧合的檢查

**困難。** 這個系統的中心主張是「我們的檢查是真的」。
那就必須預期**檢查本身**會壞掉——而且壞掉的方式，是它「看起來有在檢查」但其實在回報一個巧合。

**為什麼難。** 因為這種缺陷不會讓測試變紅。它會讓測試變綠。
開發期間先找到的五筆：

| | 缺陷 |
|---|---|
| 1 | 一個從未被評估過的約束，被記錄成「已滿足」 |
| 2 | 一個前置條件，是被另一個 process 的副作用滿足的，不是被受測物滿足的 |
| 3 | 一個空洞的分支：沒有東西可檢查時，回報「檢查通過」 |
| 4 | 一個測試把缺陷編碼成需求，於是修掉缺陷就會弄壞測試 |
| 5 | 宣告了、但從來沒實作的 evaluation oracle |

**前四筆讓正確的行為看起來壞掉；第五筆讓沒被證明的行為看起來被證明了。**
這個不對稱，就是第五筆活得最久的原因——也是為什麼「讀 diff 的 review」抓不到它，
而「把部署的系統當對手來跑」抓得到。

**怎麼改。** 每一筆都變成一條規格修訂，而不是一個 point fix。
並且在 analysis report 裡開一節 §5.4「驗證那個 verifier」，把每一筆全部列出來、包含沒修的。

**代價。** 這一節讓報告變長，而且它讀起來對我們不利。那是刻意的。

---

### 3.2 宣告了但從來沒實作的 evaluation oracle（第 5 筆，第一筆方向樂觀的）

**困難。** dev set 的案例註記寫著「harness 會自己抓那張表、套一樣的排序鍵、比對」——
**那段程式碼從來沒有存在過。**

**為什麼難。** 這讓我們最強的正確性宣稱變成不可否證的。
`check_evidence` 實際做的是：重新抓 artifact、重新雜湊、在裡面重新定位每個宣稱的值——
那是對「支持這個宣稱的證據」的真獨立檢查，但**不是對「正確答案」的獨立推導**。
在 r1 上，OP-4 和 OP-5 的 `independently_checked` 都是 **0**——
偏偏那兩筆是我們自稱「結構上防捷徑」的記錄。
**於是「verified-but-wrong = 0」這個宣稱，在最需要它的地方是不可否證的。**

一個沒辦法登記事件的儀器不會產出零，它產出的是「沒有資訊」；把它報成零，
就是我們自己對自己犯下這個系統存在要防的那個缺陷。

**怎麼改。** 幫 OP-4 建真的推導：harness 自己去抓那篇文章、找到帶有指名欄位的表格、
**從那個欄位自己的值決定要用數值還是字典序**、排序、比對第一列。
r3 是它第一次在計分輪次裡跑——DEV-01 的 8 個 cell 全部一致。
OP-5 **仍然沒有** oracle（展開收合區塊是互動後才存在的狀態，單純抓頁面會跟正確的 run 不一致），
而報告直接寫「它沒有」，不暗示它有。
每個案例的 `oracle` 欄位現在會指名它得到的是三種檢查裡的哪一種。

**代價。** 承認這件事花掉一段文字。被抓到「宣告了一個從沒跑過的 oracle」會花掉整個論證。

---

### 3.3 公布的七條限制裡有四條不重現

**困難。** 我們公布了七條「已知限制」。獨立 review 發現 L-1 那條的建議解法**根本不成立**，
三十秒就能重現。

**為什麼難。** 限制清單是最容易腐爛的東西：它描述的是**過去某個 build 的行為**，
而系統會變。清單腐爛的時候沒有任何測試會紅。

**怎麼改。** 把限制從「散文」改成「**一個你可以打進輸入框的任務**」，
並寫一支 `eval/limitations_check.py`，把每一條（含它宣稱的替代措辭）真的對部署跑一遍。

**第一次跑就發現七條裡有四條不照寫的方式重現：**

- L-1 的替代措辭失敗——就是 review 找到的那個。
- L-4 公布 `policy_refused`，實際是 `robots_disallowed`（實際的那個更精確）。
- L-5 的 Project Gutenberg 任務**已經開始成功了**。
  「公布一個已經不再發生的棄權」跟「公布一個已經不再有效的解法」是同一個缺陷。
- L-7 的 fixture 搜尋現在會**證明**不存在，而不是棄權。

它還順手抓到一個沒有任何測試抓到的回歸——見下一筆。

**代價。** 這條檢查必須在提交前重跑，而且報告要 commit 在 eval 結果旁邊。

---

### 3.4 A24.6 造成的步數預算回歸

**困難。** 一次無障礙樹快照佔掉一個 trace 條目，而**每個 trace 條目都會扣步數預算**——
於是「擷取密集」的 run 只剩下設計時一半的瀏覽空間。

**為什麼難。** 沒有任何測試涵蓋「一次擷取應該花幾步」。
表面症狀是 L-1 的替代措辭燒成 `budget_exhausted`，看起來像是能力問題。

**怎麼改。** 一次擷取算一步，並補測試鎖住。

**代價。** 這個缺陷是**我們自己新增的規格修訂造成的**，而且是靠「執行限制清單」才發現的，
不是靠測試。它變成 §5.4 的第 6 筆。

### 3.5 承諾集從七筆縮到四筆

**困難。** 原本承諾七筆記錄，其中 OP-1…OP-3 是在**我們自己寫的 fixture** 上。

**為什麼難。** 這不是技術問題，是誠信問題：**在自己寫的網站上量出來的成功率，等於自己出考卷自己改。**
它會讓頭條數字好看，而那個好看沒有意義。

**怎麼改。** 把那三筆**撤出承諾**，改列為「機制證據」（`/support` 上的 GS-1…GS-3），
**不進任何成功率**。承諾只剩下我們不控制的站上的四筆。

**代價。** 頭條成功率涵蓋的表面變小了。這是自己主動縮小的。

### 3.6 「推 code ＝ 部署」：在計分輪次中誤推

**困難。** 這台主機上，push 到 master **就是**部署。
產品負責人開始跑計分輪次 r2 並公告了；四分鐘後，工程 session 照樣推了一筆 commit。
計分容器在跑一個付費輪次的過程中被換掉。

**為什麼難。** 這不是程式缺陷，是**人為疏失**。而且沒有排練、沒有模擬。

**怎麼改（其實不用改，這是系統的實證）。** 系統的反應是：

- dev split **已經過了邊界**，用乾淨的檔名寫出去，裡面帶著它跑的那個 commit。它是有效的量測，也當成有效的用。
- experimental split **被切在中間**，留下 `.inflight` 標記，
  下次啟動**拒絕再跑那個 split**，而不是默默再花一次錢——操作者必須讀 log 並做決定。
- **沒有任何東西被寫成「一個看起來像完成輪次」的檔名**，也沒有任何部分結果被聚合進任何地方。

**代價，或者說收穫。** 我們寫了一長串修訂在論證這個行為（推＝部署、輪次鎖定 build、
被中斷的付費 split 必須 fail-closed）。**這是它第一次在野外被真正的失誤觸發。**
一個乾淨的 r2 只會多一行數字；這個檔案證明了機制會動。三分錢換這個，划算。

那個 `.inflight` 檔案**不准刪**——它不是待清理的殘留狀態，它是「這一輪付過錢、沒有產出」的紀錄。
刪掉就把「已花費未完成」變成「從沒跑過」，那正是會讓一輪被付兩次的誤解。

### 3.7 DEV-04：一道由「變數何時被讀取」決定成敗的硬閘門

**這一筆是整個專案技術上最有意思的一筆，而且它被修了兩次，第一次修錯了。**

**困難。** DEV-04 在 r1 通過、在 r2 失敗，**輸入完全沒變**。
run 的凍結目標是 `/wiki/Apple_Inc`，證據卻抓在 `/wiki/Apple_Inc.`。
導航步驟記的是「讀取 `page.url` 那一瞬間頁面在哪」——一輪記到後者，下一輪記到前者。
於是一個**正確的** run，在「證據是否來自計畫的那一頁」這道檢查上，**敗給了它自己的 artifact**。

**為什麼難。** 一道結果取決於「變數何時被讀取」的硬閘門**不是閘門**。
更糟的是：它之前**每一次通過都比看起來的價值低**。

**第一次修：錯的，而且錯得有價值。** 改成記 `response` 的 URL，
理由是「回應的 URL 是重導向鏈的終點，不可能跟時序有關」。這個推理是對的，**前提是錯的**。

用瀏覽器實測（不是推論）：`https://en.wikipedia.org/wiki/Apple_Inc` **回 200，完全沒有重導向**；
網址列是**大約兩秒後**被 MediaWiki 自己的 script 改掉的。**根本沒有 HTTP 跳轉可以記。**
所以第一次修會把閘門釘死在 `/wiki/Apple_Inc`——一個**永遠不會等於 artifact 來源**的值。
**它會把一個間歇性的失敗變成一個穩定的失敗。**

**真正的缺陷比那一頁更一般。** 閘門拿**一個**凍結的計畫目標，比對**一個**記錄下來的端點。
只要有任何東西移動了頁面（301、canonical 改寫），這兩個就不相等——
於是單一比對只有兩種可能行為：**放行每一次移動，或擋掉每一次移動**。
選哪個 URL 來記，就等於在這兩者之間選。
**那不是修好一道閘門，那是把一個巧合換成一個比較穩的巧合。**

**怎麼改（Amendment 26）。** 拆成兩條各自可以單獨失敗的斷言，
建立在三個都被記錄下來的值上（計畫目標、完整重導向鏈含每跳狀態、導航終點），
外加文件自己宣告的 `rel=canonical`：

1. `artifact_source_is_accounted_for_by_the_trace`——位元組來自 trace 交代得出的某一頁。
2. `landing_explained_from_the_plan_target`——那一頁是從計畫目標經由有紀錄的路線到達的。

第三條路線（canonical）正是 Wikipedia 這個案例需要、而任何端點比對都給不出來的：
當移動發生在回應之後的 script 裡，文件自己的宣告是**唯一一個不隨讀取時機改變**的已記錄事實。
它是**不可信頁面的宣稱**，所以只從任務自己指名的那一頁採信，而且只採信同源的。

**而這條路線是三條裡最弱的一條，我們把這句話寫進報告而不是留在程式碼裡。**
重導向鏈是**觀察**——我們自己的瀏覽器被從一個 URL 送到另一個，每一跳都記了狀態碼。
canonical 是**頁面對自己的陳述**。DEV-04 靠的是第二種。
撐住它的不是「我們看著 Wikipedia 把我們移過去」，而是「Wikipedia 說了它住在哪裡」，
再加上同源規則限制那個陳述能伸多遠——一個頁面只能在自己的 origin 內改自己的名字。
那是一個真的界限，但**它跟親眼看到不是同一件事**。

**代價。** fixture 要為兩條斷言各補一個負向案例。最重要的是 `/detour`：
它 301 到跟 `/moved` **完全相同的頁面**——只比最終 URL 會通過，
缺的是「一個該從 `/moved` 出發的 run 是怎麼到那裡的」交代。

### 3.8 三份文件各寫一個花費總額，同一天全部過期

**困難。** README、analysis report、以及 report 的另一節，各自寫著 `USD 0.0477`。
三個都過期了，而且其中一句（「across every scored round」）不只是舊，是**假的**——它早於一個輪次。

**為什麼難。** 這不是算錯數字，是**架構問題**：三個地方各寫各的，就會在三個不同的日子腐爛。

**怎麼改。** 做成單一來源：`python -m eval.spend_ledger` 從 ledger 讀數 ＋ 各輪 provenance 生成
`docs/spend-ledger.md`（含每個 split 花多少）；`--check` 進測試套件——
**下一次數字過期是測試失敗，不是讀者發現。**
三份文件現在都只連過去，一個總數都不寫。

**然後第一版的檢查漏掉了一個。** 檢查只抓數字，於是
`"under a tenth of a dollar"`——**同一個過期總數，用文字拼出來，寫在一個斷行後連 `spend` 都沒有的行上**——
大搖大擺地通過了。所以檢查加強成兩條規則：
金額寫成文字的字彙一律禁止（cent / dollar / pennies / a tenth of a），
以及段落層級的「spend 詞 ＋ 總量詞 ＋ 金額」偵測。拿五筆歷史違規回測，全中。

**代價。** 一個防止數字過期的機器，自己旁邊擺著一個會過期的總數——這件事本身就是同一族缺陷。

---

### 3.9 最後一天：從 histogram 推出一個自信的錯誤結論（第 10 筆）

**這一筆是這張表裡最該讀的一筆，而且重點是事件的因果鏈，不是缺陷本身。**

**困難。** held-out 輪次 r4 的 failure class histogram 顯示三筆 `robots_disallowed`。
**產品負責人讀了 histogram，指示把它寫成「我們對『一般任務』的直覺比我們自己的政策寬」的政策覆蓋面發現。**
工程 session 把它寫進兩份文件。

**為什麼難。** 那是「當下唯一擺在眼前的證據」的一個**好解讀**——而且**是錯的**。
它活下來，是因為那一輪的**摘要**裡沒有任何東西能反駁它：
**histogram 的精確度就等於 failure class 的精確度，而 failure class 不夠精確。**

**是什麼打破了它。** 點了一個連結。
那一輪的證據是一小時前才從 volume 手動搶救出來並發佈的（那一輪自己匯出了 0 個 bundle），
而提交前的最後一步，是確認「評分者打得開一筆失敗的案例」。
打開一筆之後，看到的不是規則：

```
"source": "unfetchable",
"rule": "robots.txt could not be fetched: URLError: <urlopen error timed out>",
"directive": null, "pattern": null
```

三筆一模一樣，同一個 host。查下去：
**`books.toscrape.com` 根本不發布 `robots.txt`**——它回 404，我們的 matcher 讀成不受限制。
r3 在 20 分鐘前用同一個站跑了 7 個案例，全部 `no_robots_txt / allowed=True`；現在再打，404、0.6 秒。

**真相是：在 r4 那個約 78 秒的窗口裡，一次網路逾時讓三筆 held-out 案例死在一個我們承諾的站上。**
拒絕行為本身是對的（讀不到政策就不瀏覽，那是 fail-closed inventory 裡的既有規則），
但那**不是政策覆蓋面的發現，是一次可用性事件**。

**因果鏈：一個粗到無法被檢查的匯總 → 由設定需求的那個人從它推出一個自信的結論 →
寫進提交物 → 被一份只存在了一小時的證據抓到，因為有人打開它。**

§5.4 表裡其他每一筆都是「一個檢查回報了一個巧合」。
**這一筆是我們自己，在最後一刻，做了這個系統被建來阻止模型做的事：
產出一個貌似合理、而摘要無法否證的答案。**

**怎麼改。**

- 1/8 **不動**（S-10.6：第一次跑就是分數，跑壞了不重跑），但明寫它是**下限**，
  而且 r4 量到的「可用性成分」不亞於「能力成分」。
- 五筆沒瀏覽的案例拆成兩半：三筆是那次逾時，兩筆是任務沒指名站或頁（這個是真的限制）。
- 記成 **defect 10：`robots_disallowed` 同時承載「站方禁止」與「我們問不到站方」**，
  兩種拒絕都對，只有一個標籤對。**明說不修**（凍結後才發現）。
- **也沒有加 retry**——「要多努力才算爭取到許可」是一個真的設計問題，
  在一個壞掉的輪次之後靜靜補一個 retry 上去，比留著這個缺陷更糟。
- README 加了一段給評分者的提示：看到 `robots_disallowed` 先開 trace 看 `robots.source`
  是 `rule`（站方真的禁止）還是 `unfetchable`（我們讀不到政策）。

**代價。** 一個原本很好講的故事（「我們的政策比我們的直覺嚴」）沒有了。換來的是一個更好的故事。

### 3.10 held-out r4 匯出 0 個 evidence bundle

**困難。** held-out 結果在寫檔的時候就會抽掉 per-case 細節（這是刻意的），
而 bundle exporter 讀的正是那個被抽掉的結構——
於是**七筆非成功的那一輪，匯出了 0 個 bundle**，偏偏是最值得檢視的那個 split。

**為什麼難。** 這個系統整份提交的論點是「**失敗是可檢視的**」，
而最重要的那一輪剛好是那個做不到的。評分者第一個會點的就是那七筆。

**怎麼改。** run 和 artifact 都還在計分服務的 store 裡，沒有東西丟失，只是沒被搬出來。
**不改 code、不重跑、不花錢**——用 ssh 從 volume 撈出來，八筆全部、24 個 artifact，
雜湊驗兩次（匯出時比對 store 紀錄，落進 repo 後再重算一次）。

兩個細節值得講：

- **case id 是用任務字串精確比對出來的，不是靠提交順序。**
  因為並行度是 2，有兩筆 run 的起始時間差不到 100 ms，照順序編號會編錯。
- **manifest 自己承認它不是 exporter 產的**（`"tool": "rescued-by-hand/1.0"`），
  並寫明形狀為什麼不同。**一份看起來像正常匯出的搶救，是比搶救更糟的產物。**

五筆沒有 artifact，那是**結果**不是漏撈：它們在任何導航之前就被拒絕，沒有頁面可抓；
對一次拒絕而言，證據**就是** trace——匹配到的規則、被比對的 URL、停在哪一步。

**代價。** 這是手動搶救，它應該是 exporter 的職責。缺陷記著，exporter 沒修。

### 3.11 PM／ENG 兩個 session 的角色分離

**困難。** 整個系統是由 AI session 建的。那要怎麼避免「自己定義成功、自己回報成功」？

**為什麼難。** **一個同時定義成功並回報成功的 session，一定會回報成功。**
那跟「一個同時作答又自己驗證的 agent」是同一個缺陷，只是高了一層。

**怎麼改。** 兩個 Claude Code session，角色刻意分開：

- **產品負責／驗收 session**：擁有規格、寫驗收標準、裁決爭議，**從不寫產品程式碼**。
- **工程 session**：照凍結的規格實作，**從不決定什麼叫「正確」**。

規格是凍結文本，只能用**編號修訂附加在後面**，永遠不改前面已凍結的字。

**這個分離實際擋下了什麼**（這些不是假設，都真的發生過）：

- OP-7 的承諾寫得對、實作卻鎖死在單一商品——**support matrix 對外為假**。
  問「一個商品的 UPC」以外的任何商品，都會掉到 T-EXPERIMENTAL。
  承諾是按 `site × operation` 寫的，頁面應該是參數。這是驗收方發現的，不是實作方。
- L-1 公布的替代解法根本不成立。
- 宣告了但沒實作的 oracle。
- 逐句驗收抓到的文件脫鉤：README §3 已經縮成四筆承諾，§4 還寫著 "seven records"；
  §8 寫「SSRF probe 是 safety suite 的一部分」，而 §7 寫「safety suite 沒建」——同一份文件自打臉；
  L-5 的表格列寫 gutenberg.org，程式碼裡是 MDN，而同一節下面三段的 bullet 自己說了是 MDN。
- 一道空洞的檢查（`scope` 不是已知值時，回報「通過」但什麼都沒比對）——
  **在修好第 7 筆缺陷的那次改動裡，把第 1 筆種了回去。**

**代價。** 這個分離很貴：每一次驗收都是一輪往返，而且驗收方會擋下工程方想推的東西。
**但反過來的成本是整份提交的可信度。**

**同時要誠實的一點**：§3.9 那筆最嚴重的錯誤結論，**是驗收方自己下的**。
分離擋得住「實作方誇大實作」，擋不住「驗收方讀了一個太粗的匯總」。
擋下它的是證據，不是流程。

### 3.12 送審當天：那一頁從來沒有任何測試打開過（第 11 筆）

**困難。** `/runs/{id}`——trace、artifact 出處、拒絕理由所在的那一頁，也是整份提交
「失敗是可檢視的」這個論點的落點——**回了三天的 500**，橫跨 `r2`、`r3`、`r4` 三輪計分。

**成因。** 加入 locator memory 的那次 commit，在 `run.html` 加了一段讀 `build.locator_memory`
的區塊，卻沒把 `build` 加進 `run_detail` 的 context。Jinja2 的 `Undefined` 可列印、可迭代、
可做布林判斷而不出聲，**只在被存取屬性時才拋**——所以壞掉的剛好只有這一條路由。

**為什麼難。** 三層防護剛好都不在位置上，而每一層失效的理由都不同：
守前端「宣稱不得過期」的那組測試取的是 `/` 與 `/support`，兩者都有傳 `build`，於是測試是綠的；
輪次 harness 從 store 讀 run 而不是從頁面讀，所以一輪計分不可能察覺頁面掛了；
模板的失敗本身在構造上就是靜默的。這裡沒有壞運氣——**這一頁沒有測試，因為它從來沒有過測試。**

**怎麼改。** context 補一行。真正必須跟它一起交的是測試：**每一種 terminal status 各一筆 run，
取這一頁，要求 200**，另加一筆未完成的 run（走 SSE 分支）與一筆帶 trace／artifact／verdict 的。
把驗證：拿掉那行 fix，十個測試裡九個失敗。`/runs/{id}` 同時進了部署後的煙霧測試清單。

**它是怎麼被找到的。** 送審當天有人做了評審會第一個做的事：點開一筆 run。

**為什麼這一筆在凍結後仍然修。** 它不動任何一輪的數字——沒有任何計分結果讀過那個頁面——
而另一個選項是交出一個「可檢視性本身無法被檢視」的系統。第 8、9、10 筆不修的理由在這裡不成立。

**代價與方向。** 前十筆都是「一個檢查回報了巧合」；這一筆是**完全沒有檢查**，
而且缺在最該有的那一頁上。前十筆問的是「我們的檢查是不是真的」，
這一筆問的是「**我們有沒有替最重要的東西寫過檢查**」——那是一個不同、而且更難自問的問題。

### 3.13 隔天：同一頁，動起來之後沒有人看過（第 12 筆）

**困難。** `run_b99d78d84a67` 在 **13.12 秒**就以 `succeeded_verified` 結束，
而使用者頁面上的進度指示**轉了兩分鐘以上還在轉**。

**成因。** `run.html` 的進度只有 `es.onmessage`，沒有 `es.onerror`、沒有 timeout、沒有輪詢後備。
`EventSource` 在重連拿到 HTTP 錯誤時會**永久放棄**並觸發 `onerror`——
而我們自己每次部署換容器的 12–23 秒斷線，從瀏覽器看正是這個形狀。
沒有人接住，頁面就停在最後一則進度文字上。

**為什麼這不是修飾。** 「顯示執行進度」是評分項，而這個壞法是**靜默的**：
頁面看起來還在工作，實際上 run 已經成功。
**我們自己的介面，對我們自己的執行狀態，產出了一個貌似合理而錯誤的說法**——
正是這整份提交在反對的那種失敗，只是這次發生在我們自己身上。

**怎麼改。** 出錯、或安靜滿 20 秒，就關掉串流、改成每 3 秒取一次 `/api/runs/{id}`，
`state` 變 `done` 就重新載入；滿 5 分鐘就停下來說「這一頁已停止自我更新，請重新整理」，
而不是無限轉。**而且切換是明講的**——頁面用文字說出「即時更新已關閉，現在改為輪詢」。
無聲降級只是把同一個缺陷換一件安靜的外衣：讀者必須能分辨自己看的是哪一種傳輸。

**它和第 11 筆是同一個洞的兩半。**
第 11 筆是**那一頁沒有被請求過**；第 12 筆是**那一頁動起來之後沒有被看過**。
昨天為第 11 筆補的測試只涵蓋渲染——它回答「它會不會回來」，
不回答「它在跑的時候有沒有一直說實話」，而後者才是一個介面最容易在
沒有人寫下任何一句假話的情況下說謊的地方。

### 3.14 最後一次審查：三句我們用來描述自己、而且已經過期的話（第 13–15 筆）

一位獨立審查者在部署上跑完一輪，帶回四筆。其中三筆是缺陷，第四筆是「頁面沒把話講完」。

**第 13 筆——被砍掉的工作被顯示成排程中。** `/coverage` 對 `injection_detected`
顯示 `due_at "M6"` / 尚未輪到，而 README 宣稱那一頁「明說沒有任何程式路徑到得了」。
頁面沒這樣說。安全測試組是**被砍的，不是排程中的**，
所以那個顯示的方向是**樂觀的**——而且它長在我們的誠實面上，還順手把內部里程碑代號
洩給一位無從得知 M6 是什麼的讀者。
**修的是頁面，不是那句話**：資料層把「刻意未實作」與「尚未輪到」分成兩件事，
前者不帶任何未來里程碑，只帶一個理由。

**第 14 筆——一個事實的第二份副本。** `app/coverage.py` 把當前里程碑硬編成 `M4`，
而 `app/buildstate.py` 說 `M5`：兩個獨立來源，已經漂開。
這裡值得把話說準：**修掉它並不會讓 `gate_passes` 變 true**——沒有任何值宣告在 M5，
到期集合兩邊一樣；那十個 failure class 標成 overdue 是因為它們在這個部署上**真的沒被產生過**，
那正是這一頁要講的事，不是缺陷。漂移本身才是缺陷：只要哪天有一個值宣告在 M5，
它就會被一個沒人記得要改的字串靜靜標成「還沒輪到」。現在從 build 讀，一個來源。

**第 15 筆——用位置指路，指在一張會重排的清單上。** 首頁寫「最前面幾筆是啟動時預先執行的」，
實際上清單是新的在前，示範一旦有人送任務就會往下沉。排序本身沒有錯，
錯的是那句話：改成用 `pre-executed` 標記指認，而不是用序位。

**第四筆不是缺陷，是話沒講完。** locator memory 的計數器全零
（`rows_stored 6 / uses 0 / hits 0 / heals 0`）是**正確行為**——記憶體只在定位失效時啟用，
正式環境沒有失效過。但頁面沒說，讀起來像「建了但是死的」。
我們對自己的 oracle 講過「一個無法登錄事件的儀器產出的零不是結果」，
這條標準要一併用在自己身上：`/healthz` 現在會說出這是哪一種零——
**已寫入的列數證明寫入路徑是活的，所以這個零是量到的，不是沉默。**

**這三筆共用一個主題。** 每一筆都是一頁用散文描述我們自己，
而每一筆都朝著對我們有利的方向悄悄過期了。三筆全部是由**使用部署系統**、
而不是讀 repo 的人抓到的——和第 10、11、12 筆同一種方法。
build-state 推導存在的理由正是「程式碼變動時散文沒有理由跟著變」；
它涵蓋得了能從程式碼讀出來的宣稱，而這三筆正好是讀不出來的那種。
改法每一次都一樣：**讓頁面陳述它能推導出來的東西**——
用理由取代里程碑、用 build 自己的里程碑取代副本、用標記取代序位。

**測試的誠實邊界。** pytest 跑不動瀏覽器的事件迴圈，所以新測試斷言的是
「這一頁把後備路徑送出去了」，不是「後備真的會觸發」。這是比較弱的宣稱，
測試自己的 docstring 就這樣寫，行為本身是對線上部署手動驗的。

### 3.15 隔天再一次審查：五筆，其中一筆是前一天的修法（第 16–20 筆）

第二位獨立審查者只用瀏覽器、不讀產品程式碼，又跑出十一筆；八筆是文件說了一件頁面上不成立的事，
文字當天就修完，剩下五筆要動程式碼。**第 16 筆是這五筆裡唯一真正難堪的，因為它就是第 15 筆的修法。**

**第 16 筆——一句過期的話，被換成一句從來沒真過的話。** 第 15 筆改成「用 `pre-executed` 標記指認
示範，不要用位置」。審查者去數了：**整張表格 0 列帶那個標記，也沒有任何一列顯示擷取日期**。
原因是那些示範是「因為夠新」才被選進表裡的，而一個已經服務過七十筆的部署上它們早就不在窗口內。
現在改成用旗標本身選那幾列，而且同一個任務的示範列與最新一筆實跑列**兩列都留**——
它們是關於同一個任務的兩個不同宣稱。

**第 17 筆——那段用來正當化去重的話，指向一個 405。** 首頁說「每一筆執行仍然列在 `/api/runs`」，
而 `GET /api/runs` 只收 POST。**去重不算隱藏，前提是那個端點會回答**；它三個部署以來都沒有。
現在寫出來了：全部執行、新的在前、截斷時明講還有多少。

**第 18 筆——`/coverage` 把自己講反了。** 它說「本次部署自上次重啟以來」以及「重新部署會清空這張表」，
而那個 ledger 就在掛載的 volume 上、跨部署累計。相信那兩句話，一長串「從未產生」會被讀成
*我們剛重啟過*——正好把這一頁唯一要支撐的結論反過來。現在那句話從 store 自己的
`persistent` 旗標渲染。

**第 19 筆——錯的標籤，暴露了一支比它自己的宣稱更寬鬆的檢查。** L-1 的補救措辭公布
`failed / budget_exhausted`，實測是 `failed / verification_mismatch`
（`run_fa5239cbb696`，25 步走滿，verifier 讀到表格自述「未排序」而拒絕該宣稱）。
標籤錯不是重點：`eval/limitations_check` 重跑過全部七條、回報七條全部重現，
因為它對補救那一半**只比對 terminal status**。現在 failure class 也比對，
`None` 代表「本條主張沒有 class」而且會被檢查，刻意不釘的必須寫 `UNPINNED` 明講。
修完之後對線上重跑一次：改之前不重現，改之後重現。

**第 20 筆——一個二元欄位只渲染否定的那一半。** 執行詳情頁在不算成功時顯示
`does not count as success`，算成功時什麼都不顯示——而我們的導覽叫讀者信這個欄位、不要看狀態字。
於是它的缺席同時代表「成功了」和「還沒結束」。兩半都渲染了。

**這五筆的共通規則，值得單獨寫一行：測試要拿渲染出來的頁面去比對程式碼推導出來的值，
不能比對那句話本身。** 第 16 到 18 筆之所以能在一次專門在找它們的審查裡活下來，
就是因為附近的測試只釘住了散文；一段文字自己斷言自己，等於什麼都沒檢查。
新增的測試因此是這樣寫的：第 17 筆斷言那個端點**比它所正當化的表更長**，而不只是「存在」；
第 18 筆斷言頁面的說法與 `storage_status()["persistent"]` 一致，而不是斷言某個字串在不在。

## 5. 誠實的自評

### 5.1 做得好的

**一、「模型提議、程式碼裁決、裁決對象是儲存的位元組」這個架構是對的，而且便宜。**
驗證在延遲上幾乎不佔成本，卻讓「答錯還說自己對」變成一件結構上困難的事。
三輪計分下來 **verified-but-wrong = 0**，而且 r3 有一筆是**真的獨立推導出正確答案**去比對的（DEV-01，8 個 cell 全中），
不只是「在證據裡重新找到」。

**二、把限制清單從散文改成可執行的任務。** 第一次跑就抓到七條裡有四條是假的。
一份不能執行的限制清單，會在沒有人發現的情況下腐爛。

**三、三輪計分結果全部 commit，包含難看的那兩輪。**
一個「只因為跟它不合的輪次被刪掉才活下來」的數字不是量測。

**四、兩個 session 角色分離，而且分離真的擋下了東西。**（§3.11 列了清單。）

**五、held-out split 已公布，而且雜湊在跑之前就 commit 了。**
`shasum -a 256 eval/test-set.md` 把「分數、產生它的檔案、早於它的雜湊」三者閉環，
**不需要相信我們**。validation 公布但未執行——那是「我們真的把它扣住了」的唯一物證。

### 5.2 做得不夠的

**一、承諾的路由太窄，而我們自己量不到。**
held-out 的四題 declared 有兩題沒到達承諾表面。
我們自己的 split 量的是「**被接受的任務答得多好**」，
量不到「**多少合理的任務會被接受**」——因為每一個我們寫的案例，都是由已經知道 router 吃什麼的人寫的。
**如果再多一天，我不會拿去做模型上的工作。**
我會替每個承諾記錄建一份**由沒讀過 router 的人寫的措辭語料**，拿它去評 admission gate——
就是 `docs/m4-fail-closed-inventory.md` 已經對 out-of-scope classifier 用的那套兩面語料紀律，
套到分層判定上。

**二、r4 的 1/8 有一大塊是可用性，不是能力，而我們沒有 retry。**
三筆 held-out 案例死在一次 robots.txt 取得逾時上。拒絕是對的，標籤是錯的，而且我們沒修。

**三、OP-5 沒有獨立 oracle。**
展開收合區塊是互動後才存在的狀態，單純抓頁面會跟正確的 run 不一致。
所以那筆記錄的正確性，完全靠我們自己的 verifier——**而那正是被檢查的東西本身**。
報告直接寫這件事，不暗示它有。

**四、DEV-04 靠的是三條路線裡最弱的一條。**
它通過，是因為 Wikipedia **說了**自己住在哪裡（`rel=canonical`），同源規則限制那個陳述能伸多遠。
那是一個真的界限，但**跟親眼看到重導向不是同一件事**。

**五、跨家族的策略轉換，沒有任何一筆已 commit 的結果檔記錄到真實案例。**
機制建好了、測試套件有在跑它、healing demonstration 有一個——
但**田野證據是一個示範，不是一個比率**。
一個我們有信心、卻指不出正式案例的機制，正是這份報告應該讓人不舒服的那種宣稱。

**六、三筆缺陷（8、9、10）在凍結後發現，明說不修。**
修任何一筆都代表「量測系統的那一輪」跟「計分 held-out 的那一輪」之間有 code 變動——
所以取捨是「比較乾淨的程式碼」對「兩輪描述同一個 build」。**程式碼輸了。**

**七、Amendment 26 沒有被寫回規格。**
A26 在 `README.md`、`docs/analysis-report.md`、`docs/m4-fail-closed-inventory.md`
和 `tests/test_build_claims.py` 裡都被引用，但 `docs/task1-spec.md` §16 只有 25 條。
**一個被四份文件引用、卻不存在於它應該存在的地方的編號修訂**——
這正是這份報告從頭到尾在講的那一族缺陷，發生在寫這份報告的當下。寫在這裡，而不是安靜補上。

### 5.3 最後一句

**這份提交的頭條數字（held-out 1/8）比一個吹得比較鬆的產品難看很多。**
但這裡面每一個數字都帶著它的條件、都指得出產生它的位元組、

**一個組織良好的數字，不等於一個真的數字。**
