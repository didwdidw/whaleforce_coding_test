## 2. 執行效能

### 2.1 延遲

取自 `r1`，在部署環境內，橫跨 25 個真實案例。分路徑報告。

| | 決定性路徑 | 模型驅動，declared (n=12) | 模型驅動，experimental (n=10) |
|---|---|---|---|
| 端到端中位數 | **0.16 s** | **5.85 s** | **12.18 s** |
| 端到端 p90 | 0.16 s | 13.07 s | 27.73 s |
| 端到端最大 | 0.16 s | 16.43 s | 30.29 s |
| 首個結果時間中位數 | — | 5.13 s | 12.13 s |
| 供應商時間中位數 | **0.00 s** | 1.65 s | 3.74 s |
| 佇列等待中位數 | 0.01 s | 0.01 s | 0.01 s |

三個值得從這裡讀出來的結論：

**experimental tier 約為 declared tier 的 2.1 倍成本。** declared 記錄跑的是凍結計畫，模型只被問「下一步做什麼」；experimental 得自己弄清楚沒人描述過的頁面形狀，更多呼叫、更多擷取。

**供應商時間只佔 wall clock 少數**——declared 中位數的 28%、experimental 中位數的 31%。其餘都是瀏覽器：導覽、等文件穩定、擷取。優化模型不會讓這個產品變快多少。

**驗證不是昂貴的部分。** 在儲存的 artifact 內做決定性重新解析，在上述任何中位數裡都不是可分辨的項——lxml 解析加 XPath，數十毫秒對上 5–12 秒的 run。這個設計真正付出的代價在**儲存**（§4）與**棄權**（§3），不在延遲。

### 2.2 冷啟動

兩個數字，因為它們回答不同問題，混為一談曾是我們修正過的缺陷：

| | 量測值 |
|---|---|
| **部署到可用**——推送落地、容器建置、app 開始回應 | **112–176 s** |
| **對正在使用的使用者造成的中斷**——請求失敗而非排隊的窗口 | **12–23 s** |
| **冷但已部署容器的第一個請求** | **未量測**（見下） |

第二個數字才是評審在意的，而且比第一個小一個數量級。它是從外部量的（行程無法為自己的不可用計時）。已 commit 六筆讀數（`eval/results/coldstart-deploy-*.json`），最近一筆（推送十個 commit）為 **141.1 s 到任務完成、其中 16.3 s 斷線**。六筆的離散大多來自平台在容器置換前的建置佇列。

**冷抵達未量測，理由寫出來而不是把數字估出來。** 它需要一段長到讓平台驅逐容器的閒置窗口，而本專案的每個窗口都被部署或計分輪次佔滿；我們也從未確認這個部署真的會變冷。估計值只會是穿著量測外衣的猜測。

我們自己的假設錯了，是量測糾正的：A11.2 假設冷抵達會主導評審感受到的等待，五筆讀數顯示主導的是建置佇列。這被記為「被自己的資料推翻的假設」，而不是悄悄拿掉。

緩解手段是設計而非花錢：首頁掛有預先執行好的 run（含失敗），完全不需容器工作即可檢視（S-11.5）。我們選擇接受冷啟動，而不是付錢避開它。

### 2.3 吞吐與負載

取自 `load-local-427cd96.json`，決定性路徑、迴圈中無模型呼叫。

| | 量測值 |
|---|---|
| 設定容量 | concurrency 2，queue depth 2 |
| 飽和起點 | 一次 **5** 個的 burst 是第一個被拒的 |
| 持續吞吐 | 45.7 秒窗口內 **430 runs/分鐘**，6 clients，328 完成，421 在 admission 被拒 |
| 該負載下佇列等待 | 中位數 0.23 s，最大 0.47 s |
| 該負載下 run 時長 | 中位數 0.21 s，最大 0.50 s |

**那個吞吐數字不是能力宣稱，不得如此引用。** 這些 run 只花約 0.2 秒，所以 burst 還在抵達時佇列就在下面排空了。模型驅動的 run 要 5–30 秒，burst 期間什麼都不會排空，因此第一個超過 `concurrency + depth`（在途四個）的提交就開始被拒。飽和點 5 是工作負載的性質，跟佇列的性質一樣多，結果檔自己有寫。

**429 是設計出來的狀態，不是錯誤頁。** 被拒的 run 是帶 `Retry-After` 的 `blocked / queue_full`（S-11.10b），在 API、run 頁面與 health endpoint 上都讀作終態，沒有請求被靜默丟棄。

### 2.4 記憶體——真正的約束

| | |
|---|---|
| 負載下觀測峰值 | 4 GB 中的 **2,320 MB** |
| Swap | 平坦在 102 MB——量測期間系統沒有掉進 swap |
| 餘裕 | 峰值時**尚餘 1,457 MB**，兩個瀏覽器都起著。方法：從輪次重啟前 30 秒到結束後 5 分鐘，每 10 秒取樣 host `free -m`。基線 used 1,795 MB；輪次結束一分鐘內回到 1,836 MB 並平穩五分鐘，代表記憶體是被歸還而不只是沒被耗盡 |

限制併發度的是記憶體，不是 CPU、不是錢。**一個行程兩個 browser context**（而非兩個行程）是讓 concurrency 2 塞得下的決策；量測是「為什麼是 2 而不是 4」的答案。

## 3. 成本

### 3.1 已量測

| | |
|---|---|
| 模型驅動 run 的成本中位數 | **USD 0.0019** |
| 決定性路徑的 run | **USD 0**——無模型呼叫 |
| 每輪與累計總額 | **[`docs/spend-ledger.md`](spend-ledger.md)**；累計計費支出為 **billed USD 0.1515** |

**本專案所有總額都在單一生成檔中，本文不自帶任何總額。** 過去有三處各帶一個花費數字，三處在同一天全部過期，其中一處（「所有計分輪次的供應商總支出」）不只是舊，而是錯的，因為它早於某一輪。`python -m eval.spend_ledger` 從讀數與輪次 provenance 重新生成 ledger，`--check` 會在 committed 副本過期時失敗——下一個過期的總額是測試失敗，而不是讀者發現的東西。

那裡的每個數字都是**計費**支出。以名目價格計算免費額度用量量到的是真實的東西，但那不是錢；把兩者當成同一件事曾差點在花費為零、跑了約 125 個 run 之後擋掉我們的公開 demo。兩者都追蹤，只有一個叫成本。

### 3.2 這個數字依賴什麼

以下任一改變都會使該數字失效：

- **價格**：輸入 USD 0.25 / 1M tokens，輸出 USD 1.50 / 1M tokens。
- **輸出上限**：每次呼叫 2,048 tokens、每個 run 16,000。調高任一項都會抬高單一 run 的成本天花板，而已量測的中位數對新天花板毫無資訊。
- **輸入大小，這是主導項。** 在此價格下輸入的每 token 成本比輸出便宜 6 倍，而 run 是輸入密集的——一個量測到的 declared 案例用了 10,341 input tokens 對 328 output。決定輸入大小的頁面縮減因此是系統中最大的成本槓桿，改 element cap 比換模型影響更大。
- **每 run 呼叫數**：最多 12（8 次探索、4 次 recovery）。典型 declared run 用 **2** 次探索呼叫；一次 recovery 加一次差不多大小的呼叫，所以有 recovery 的 run 約為乾淨 run 的 1.5 倍，而非數倍。
- **重問算兩次。** 被我們自己的輸出上限截斷的回覆會重問，兩次都上帳單也都計入 budget。由此產生的失敗（`output_truncated`）歸類為我們的而非供應商的。

harness 用來估算輪次成本的預測常數是 `EVAL_USD_PER_RUN = $0.0042`，取自較早 commit 上最貴的 dev 案例。`r1` 最貴的案例來到 **$0.0048**——尾端超過了常數，被 1.5 倍安全係數吸收。這就是安全係數的用途，也是為什麼該常數被文件化為「上一輪的最大值」而非參數。

### 3.3 誠實的框架

一個 run USD 0.0019，**成本不是這個產品的約束，我們不該假裝它是照著成本約束來工程化的。** 有意思的成本問題是反過來的：什麼條件成立時它才會變貴？那是可擴展性一節。

我們在這裡**投入過度**。spec 大約有五條修訂在處理花費上限、ledger 與 credential 拓撲，保護的支出規模只在 [`docs/spend-ledger.md`](spend-ledger.md)、不在別處（也不在這句話裡，那正是前三個過期數字的形狀）。這在 §6 被記為 process finding 而非藏起來。

## 4. 可擴展性

不是成長預測，而是誠實交代什麼會先壞。

**記憶體最先綁死。** 峰值 2,320 MB / 4 GB，一個 browser context 要 550–800 MB。下一個併發度級距需要的只有 RAM。系統其餘部分已經是 per-run 無狀態。

**乾淨可擴展的部分。** evidence store 內容定址、僅附加；verifier 是 (儲存的 artifact, 凍結的 postcondition) 的純函式；run 之間不共享狀態。水平擴展就是同一個佇列後放更多瀏覽器容量。

**不可擴展的部分。**

- **儲存。** artifact 是成長項：真實頁面的 DOM 約 50 KB，accessibility snapshot 再加 22–32%，每次擷取各存一份——約 0.2–0.5 MB / 模型驅動 run。`r1` 的 dev split 為 15 案產生 5.95 MiB 的隨附證據。保留期 14 天、到期記為有日期的狀態而非懸空參照，所以磁碟有界——但界線來自政策而非架構，較重的工作負載需要重新檢視政策而不是加硬碟。
- **供應商的速率限制比我們的瀏覽器先綁死。** 15 requests/分鐘，設定時留 2 的邊際。以 12 秒中位數、2 個併發 run 計，系統提供約 10 個模型驅動 run/分鐘、每個 2–3 次呼叫——所以帳號限制大約在**五個併發 run** 就到頂，低於記憶體會擋住我們的點。不提高供應商限制而只提高併發度買不到任何東西。
- **各站點的禮貌性限制獨立於我們的容量限制每站吞吐。** 目標站的 crawl delay 或請求上限不管我們閒置多少容量都是綁死的，而且那也不是我們想繞開的限制。
- **我們量到的唯一非線性劣化是併發瀏覽器的記憶體**，這就是併發度為 2 的原因。第三個 context 的成本不是三分之一——要塞得下的是峰值而不是平均。

**100 倍量時什麼會改變設計。** 決定性路徑可擴展，模型驅動路徑不可。declared 記錄以 0.16 s、USD 0 執行凍結計畫，100 倍是形狀已知的容量問題。100 倍的模型驅動路徑則是另一個產品：先撞供應商速率限制，再撞自己的 token 帳單；誠實的答案是我們會把量花在**宣告更多記錄**而不是更多推論。但整份送審所依賴的那個但書仍在：這只涵蓋有人宣告並評估過的表面，而 experimental tier——評審沒見過的任務落點——正是不會隨規模變便宜的那部分。

## 5. 正確性如何驗證

這一節是產品存在的理由。

### 5.1 這條鏈

一個主張只有在**完整儲存的 artifact** 內做決定性重新解析、定位到宣稱的值、綁定到任務指名的 label、且對照瀏覽器開啟前就雜湊的 postcondition，才算 `verified`。模型的斷言是這個檢查的輸入，永遠不是它的替代品。

三個可查核的性質：**第三方可重現**（artifact 公開於 `/api/artifacts/{id}`）、**不受頁面漂移影響**（檢查跑在儲存的 bytes 上）、**不能靠巧合滿足**（值結構性綁定到 label）。

### 5.2 兩道 gate 與其適用範圍

| Gate | 結果 |
|---|---|
| Verified-but-wrong 主張 = 0 | **在 `r1` 成立**——沒有任何 run 回傳過被獨立重檢發現與 artifact 內容不同的值。依賴它之前請先讀 §5.3 |
| `verified` 結果的必要證據覆蓋率 = 100% | **在 `r1` 成立**——每個標為 verified 的主張都帶著它被重新抽取自的 artifact id 與 SHA-256，harness 逐一重抓並重新雜湊 |

**這兩道 gate 成立於我們的評估集、且是第一次執行的結果。它們不是系統層級的保證**，任何暗示相反的措辭依我們自己的 spec 就是缺陷。held-out split 上 n=8，一個失敗就移動 12.5 個百分點；因此一律報告區間，絕不報裸的點估計。

### 5.3 oracle 實際檢查什麼——以及哪裡根本沒有

依程式碼而非依意圖寫。dev set 的案例註記曾描述 oracle（「harness 抓表、套用相同排序鍵、比對」），那些**從未被實作**。`eval/harness.py:check_evidence` 實際做的是：透過 API 重抓每個 artifact、對擷取時記錄的 digest 重新雜湊、在其中重新定位每個宣稱的值。那是對*主張背後證據*的真實獨立檢查，**不是**對正確答案的獨立推導。

| 記錄 | 什麼在獨立檢查它 | 那留下什麼未檢查 |
|---|---|---|
| **OP-4** — 排序表格、讀首列 | **A25.4 起有獨立推導。** harness 自己抓文章、找到帶指定欄位的表、依該欄自身的值判定數值或字典排序、排序並比對首列。這是這裡唯一能說出「一個 *verified* 的 run 對世界的認知是錯的」的檢查 | 文章是否在 run 與檢查之間改變。無法歸因的抓取回報 `not_comparable`，絕不記為失敗 |
| **OP-5** — 展開摺疊區塊、讀值 | 同上機制，但 `independently_checked` 為 **0** | **全部——而且比寫下這一行時知道的更多。** 正確性完全依賴產品自己的 verifier，沒有任何獨立 ground truth；後來獨立審查者發現，在兩個標準案例上 verifier 根本沒有在檢查那個值，因為 planner 從來沒有替它建立宣稱（Amendment 28，§5.4 第 21 筆）。那個 `2/2` 量的是狀態轉換。宣稱現在會被建立，而這兩題隨即綁不上：`r5` 上分別是 `unsupported / postcondition_unmet` 與 `failed / budget_exhausted`。**這個 record 現在示範的是狀態轉換，並且拒絕報出它綁不上的值——就這樣而已** |
| **OP-6** — 分類清單、清單層級事實 | 列舉會**逐成員**對儲存的 artifact 重新推導——本集中最強的檢查，也是「不存在」所依靠的 | 多頁分類的列舉是否完整（這是 L-3，它棄權而不猜） |
| **OP-7** — 產品頁上帶 label 的欄位 | 值是純量，透過 label anchor 在 artifact 內重新定位 | label anchor 是否是人類會挑的那個。以及該記錄曾寫死在單一產品（§6） |
| 拒絕（robots、政策） | 命中的規則被引用，可對線上 `robots.txt` 重新查核 | 無實質缺口 |

**後果與變化。** 一個無法登記它要找的事件的儀器，產生的不是零，而是沒有資訊；把那報告成零，就是這個系統存在要防止的缺陷，由我們對我們自己犯下。在 `r1`，OP-4 與 OP-5 兩者都是這個狀態。

OP-4 現在有真正的推導，而「數值 vs 字典排序」的區別正是它值得蓋而不只是揭露的原因：同一欄反向排序是完全不同的首列，兩種順序在頁面上看起來都很合理。**OP-5 仍然沒有**——展開摺疊區塊是只在互動後才存在的狀態，純抓取會與一個正確的 run 不一致，其正確性靠產品自己的 verifier。`eval/dev-set.md` 中其他每個案例的 `oracle` 欄位現在都指明它得到三種檢查的哪一種，而不是十五案全都宣稱一個沒有任何程式碼執行過的推導。

揭露這件事的代價是一段文字；被抓到宣告了從未執行的 oracle，代價是整個論證。

### 5.3.1 r1 與 r2 的差異量到什麼、沒量到什麼

dev split 對部署評分過兩次，頭條從 **6/11** 移動到 **9/11**，而誠實的讀法比這個數字看起來窄。

**r2 不是單一變因的改動，而原本要它是的計畫被事件超越了。** 它本應只帶入評分器的 corpus 修正，好讓 `r1 → r2` 把量測缺陷與產品改良分離。它沒有：它跑的 build 同時帶著 OP-7 參數化、n-claim postcondition 與 locator memory。engineering session 在等一個只有 product owner 能做的操作時，繼續依修訂的順序往下做，而原本要用來分離的輪次邊界在那些改動落地前就花掉了。這是排程錯誤，並被記為排程錯誤。

**真正分離出量測缺陷的東西，比輪次邊界更強。** r1 判負的四個案例，被拿去對 **r1 自己儲存的 artifact**（從計分 volume 拉出的實際 bytes）在修正後的 corpus 下重檢。四個全部可解析，且沒有任何一個解析在 corpus 刻意排除的位置（script 字面值、class 名、`id`、`data-` 屬性、URL、註解）。量測缺陷恰好解釋 r1 頭條所缺五案中的四案，證據早於修正、不可能被它影響。

所以：**`r1 → r2` 是「移除一個量測缺陷」與「三項產品改動」擠在同一步**，而 artifact replay 是把它們分開的東西。承認混淆並指向獨立證據，比重跑一輪然後宣稱它乾淨更有價值——重跑會是第四個 build，而本文得再解釋為什麼*那個*是單一變因。

### 5.3.2 held-out split，以及它量到我們沒量過的東西

`r4` 在凍結 build 上對八個 held-out 案例評分一次，對照的檔案 SHA-256 在第一案前就已驗過。**1/8。** 同一 build 上的 dev split 是 10/11（那 10 題後來被發現有 2 題什麼都沒回答，見 §5.4 第 21 筆；修掉之後 `r5` 是 8/11）。

我們寫的集合與我們沒寫的集合之間出現這麼大的落差，是本文中最有資訊量的數字。直方圖是起點——三個 `robots_disallowed`、兩個 `policy_refused`、一個 `budget_exhausted`、一個 `postcondition_unmet`、一個成功；**八案中五案從未瀏覽**——而它*不是*終點，這一節原本就搞錯了這件事，§5.4 的缺陷 10 完整記錄。逐案打開後，那五案是兩種不同的東西：**三案是 `robots.txt` 抓取逾時**（在一個根本沒有 robots.txt 的站點上），**兩案是因為沒指名起始頁面或站點而被拒**。只有後者是系統的性質。

於是只剩五案帶有關於能力的訊號：兩案在 admission 被拒、兩案瀏覽後失敗（`budget_exhausted`、`postcondition_unmet`）、一案 verified。**n=5** 上的對半分佈不足以指認瓶頸——本節的早期版本指認了一個。

即便如此，兩組集合量的仍不是同一件事：

- dev 與 experimental split 量的是**系統對它接受的任務答得多好**。在這個問題上答案是好的，`r3` 是證據。
- held-out split 量的是**它到底接受多少合理的任務**。在這個問題上答案很差——八案中兩案因未指名頁面或站點被拒，四個 declared tier 案例中有三個沒抵達所宣告的 tier。我們建的任何東西都無法告訴我們這件事，因為我們自己寫的每個案例都出自已經知道 router 吃什麼的人。（README 也寫了這段，放在支援矩陣與分數旁邊，因為它是結論不是附錄。）

**三個 `robots_disallowed` 不是它們看起來的樣子，而這個更正比原本的讀法更有價值。** 它們最初在這裡（以及 README 裡）被寫成「我們自己的案例撞上我們自己的政策」，當成「我們對普通任務的直覺比我們選的規則更寬」的證據。那是錯的。它在一小時內被抓到，方法是打開我們剛救回並發布的證據——這也是它成為一則更正而非一份已送出文件中的錯誤主張的唯一原因。

三者實際上是：**一次暫時性網路失敗，在一個 host 上。** 三筆帶著完全相同的 `robots` 紀錄——`source: "unfetchable"`、`rule: "robots.txt could not be fetched: URLError: <urlopen error timed out>"`，沒有 directive、沒有 pattern，因為什麼都沒命中。抓不到的 `robots.txt` 依設計就是拒絕（`docs/m4-fail-closed-inventory.md` 中的一列：404 代表不受限，不可達代表拒絕），而那個動作是正確的。

問題中的站點 `books.toscrape.com` **根本沒有 `robots.txt`**，它回 404，matcher 讀成不受限。二十分鐘前的 `r3` 有七案就是這樣，現在再跑也只要 0.6 秒。**三個在我們所承諾站點上的 held-out 案例，敗給一次落在 78 秒窗口內的逾時抓取。**

由此有三點，第一點最重要：

1. **`r4` 量到的可用性不亞於能力，所以 1/8 是下限。** 數字照算——第一次執行即為回報分數（S-10.6），不因為考差就重考。但把它當成能力估計的讀者讀出了比它多的東西，這段存在就是讓那個但書跟著數字一起走。
2. **這個 failure class 混同了兩種不同事件**，那是下面的缺陷 10。「站點禁止了這件事」與「我們問不到站點」都以 `robots_disallowed` 抵達。兩種拒絕都正確，但標籤只有一種正確；只看整輪政策拒絕計數的讀者，不逐一打開 trace 就分不出來——我們一開始就沒打開。
3. **沒有 retry，而該不該有並不顯然**：重試政策抓取是在決定「要多努力才算被允許」，那正是不該悄悄做的決定。這裡把它命名為缺口，而不是在一輪考差後補進去。

三筆 tier 分歧在結構上說同一件事：兩個宣告 `T-DECLARED` 的案例被線上系統路由成 experimental。以 `site × operation` 陳述的承諾，只值它實際能被觸及的那些措辭的寬度；OP-7 寫死產品的缺陷（在凍結前發現並修好）顯然是更廣模式的一個實例，而不是模式本身。

**如果再多一天要做什麼**：不是模型工作，而是為每個承諾記錄建一份措辭語料庫，由沒讀過 router 的人撰寫，並用它對 admission gate 評分——把 `docs/m4-fail-closed-inventory.md` 已對 out-of-scope 分類器施行的雙邊語料紀律，套到 tier 指派上。拒絕本身是正確的，每一個都引用了命中的規則；比支援矩陣暗示的更窄的是它們背後可觸及的表面。

**一則對我們自己的流程註記。** `r4` 沒有匯出任何 evidence bundle。held-out 結果在寫檔當下就抑制逐案細節，而 bundle exporter 讀的正是那個被抑制的結構——於是有七個非成功的那一輪帶著零個 bundle，偏偏是最值得檢查失敗的 split。run 與 artifact 都在計分服務的 store 裡，只是沒有東西把它們帶出來。這是輪次後讀 manifest 才發現的，不是系統裡任何東西發現的——與 §5.4 每一則的形狀相同。

### 5.4 驗證 verifier 本身

一個核心主張是「我們的檢查是真的」的系統，必須預期檢查本身會出錯。共找到**二十五個**，其中**二十二個已修**。十個屬於同一物種——**一個報告了巧合的檢查**、一個根本無法觸發的檢查、或一個粗到撐不起由它導出結論的標籤。另外兩個是那個物種的鏡像——不是一個檢查報告了不實的事，而是**根本沒有檢查**——而且它們是同一個洞的兩半，在同一頁上，相隔一天被找到。十一個是第三種，全部由最後三天的獨立審查在部署上跑出來：**用我們自己的話描述我們自己的頁面**，而沒有任何東西在檢查那些話是否還成立。它現在是表中最大的一族，也是最晚才浮現的一族，因為讀 repository 找不到其中任何一個。第 21 筆自成一類，也是整組裡最難看的一個：**一個本身正確、有測試、卻只被接到其中一個呼叫端的檢查。** 前五個在開發期間找到：

| | 缺陷 |
|---|---|
| 1 | 一個從未被求值的約束被記為*已滿足* |
| 2 | 一個 precondition 是被另一個行程的副作用滿足的，而不是被受測對象滿足 |
| 3 | 一個空洞分支在無事可檢時回報檢查通過 |
| 4 | 一個測試把缺陷編碼成需求，於是修好缺陷反而弄壞測試 |
| 5 | 宣告了從未實作的評估 oracle——**第一個方向偏樂觀的** |

前四個讓正確行為看起來壞掉；第五個讓未證明的行為看起來已證明。這種不對稱正是第五個活最久的原因，也是「實際跑線上系統的獨立 review」能找到讀 diff 找不到的東西的理由。

只讀一個的話就讀第 10 個，而重點是事件鏈而非缺陷本身。

product owner 讀了 failure class 直方圖、看到三個 `robots_disallowed`，指示把它寫成關於我們政策覆蓋的 finding——以當時眼前唯一的證據來說是好的推論，而且是錯的。engineering session 把它寫進兩份文件。它能活下來，是因為該輪的*摘要*裡沒有任何東西能反駁它：直方圖精確到和 failure class 一樣，而 failure class 不夠精確。

打破它的是點了一個連結。那輪的證據在一小時前才被人工從 volume 救出並發布；送審前最後一步是確認評審能打開一個失敗案例。打開後看到本該是命中規則的地方寫著 `source: "unfetchable"`，主張一分鐘內就垮了。

所以因果鏈是：**一個粗到無法被查核的聚合數字 → 由設定需求的人從中得出一個有信心的結論 → 寫進送審文件 → 被一份存在了一小時的證據抓到，因為有人打開了它。** 這張表其他每一則都是「一個檢查報告了巧合」；這一則是**我們**，在最後一刻，做了這個系統本來要阻止模型做的事：產出一個摘要層級無從證偽的、貌似合理的答案。那是整個設計的論據——trace 就在那裡，而且它與摘要不一致——也是本專案最銳利的一次示範：一個組織良好的數字不等於一個真的數字。

第 8、9、10 是在 build 凍結後才出現的，這是它們仍然開著的唯一理由，而處理方式本身也是 finding 的一部分。修任何一個都意味著在「量測系統的那一輪」與「為 held-out split 計分的那一輪」之間動程式碼——所以選擇是在「比較整齊的程式碼」與「兩輪描述同一個 build」之間。程式碼輸了。它被寫在這張表裡跟另外二十二個並列，而不是事後靜靜修掉、再呈現成兩輪一向一致。第 8 個與 A-14b 同種：一個響亮而正確的拒絕被歸到錯的一方。第 9 個是這一節命名由來的物種——一個要人去找程式碼產不出來的證據的指示——而它在輪次進行中真的讓一位操作者受了一次驚嚇，之後才有人去讀那段程式碼路徑。

**第 11 個指向相反的方向，所以它自成一段。**

其他每一則都是「一個觸發了、而且報告了不實內容的檢查」。這一則是**完全沒有檢查**，而且缺在這份送審最依賴的那一頁上。`/runs/{id}` 是 trace 所在之處、是 artifact 出處被展示之處、是一次拒絕自我說明之處——它就是「讓失敗可被檢視」這項要求的答案，也是 README 裡幾乎每一條連結的終點。從加入 locator memory 的那次 commit 起，它一直回 500，直到送審當天：三天，以及全部三輪計分。本報告裡的每一輪，都是由一個「證據頁打不開」的部署產出的。

有三件事讓它隱形，而每一件指向不同的教訓。模板的失敗在構造上就是靜默的——Jinja2 的 `Undefined` 樂於被列印、被迭代、被判斷真假，只有在被要求屬性時才反對，所以少一個 context key 只會弄壞剛好一個分支，其餘毫髮無傷。而真正在守前端「宣稱不得過期」的那組測試，取的是 `/` 與 `/support`，兩者都有傳 `build`，於是測試套件是綠的，而且綠得很具體。至於輪次 harness，它是從 store 讀 run 而不是從頁面讀，所以一輪計分不可能察覺那一頁掛了。這裡沒有壞運氣的巧合：**這一頁沒有測試，是因為它從來就沒有過測試**，而其他東西都不在能替代它的位置上。

引入它的那次 commit，正是加入自我維護機制的那一次。它弄壞了唯一能看見那個機制在運作的頁面。找到它的方式，是有人在最後一天做了評審會第一個做的事：點開一筆 run。

修法是一行 context。必須跟它一起交的是那個測試——每一種 terminal status 各一筆 run，取那一頁，要求 200——因為缺陷從來不是那個少掉的 key；同時 `/runs/{id}` 也已進了部署 runbook 的部署後檢查，和佇列、拒絕那幾項並列。這一個**是**在凍結之後仍然修的，理由是：主要證據頁的 500 不構成兩個 build 的量測差異——沒有任何一輪的數字會動——而另一個選項是交出一個「可檢視性無法被檢視」的系統。

**第 12 個在隔天出現，在同一頁上，而它正是「第 11 筆的教訓只學了一半」的證據。** 為第 11 筆寫的測試會在每一種 terminal status 上打開那一頁並要求 200，但它對那一頁**動起來之後**什麼都沒說——而動起來的那部分有同一個洞：進度用的 `EventSource` 只有 `onmessage`、沒有 `onerror`。串流一斷（正是我們自己 12–23 秒部署窗口的形狀，見 §2.2），瀏覽器會永久放棄，而沒有東西接住它，於是頁面留著最後一行進度、繼續看起來很忙，而那個 run 早已在 13.12 秒內以 `succeeded_verified` 結束。**我們自己的 UI，對我們自己的執行狀態，產出了一個貌似合理而錯誤的說法**——正是這個系統存在要拒絕的那種失敗，只是高了一層。

修法是一個**會自報身分**的後備：一旦出錯、或安靜滿二十秒，就關掉串流，用文字說明「即時更新已關閉，改為輪詢」，然後每三秒取一次 `/api/runs/{id}`；滿五分鐘就停下來並說出來，而不是無限轉。**無聲降級只會讓同一個缺陷換一件安靜的外衣**——讀者必須能分辨自己正在看的是哪一種傳輸。

這一對值得當成一個 finding 來講，因為第二半正是第一半的修法漏掉的東西：**第 11 筆是一頁從來沒有人請求過；第 12 筆是一頁從來沒有人看著它跑。** 一個渲染測試回答的是「它會不會回來」，永遠不是「它在跑的時候有沒有一直說實話」，而後者正是一個介面最有能力在沒有人寫下任何一句假話的情況下說謊的地方。

**第 13、14、15 筆出自同一次審查、同一個下午，而它們共用一個主題。** 每一筆都是一頁用散文描述這個專案的內容，而每一筆都朝著對我們有利的方向悄悄過期了：被砍的工作顯示成排程中、一個停下來不動的里程碑、一個用它已經不在的位置去指路的示範。沒有一筆碰到任何結果。三筆全部是由一位**使用部署系統**而不是讀 repo 的審查者抓到的——和第 10、11、12 筆同一種方法，到這裡這個規律已經不隱晦了。build-state 推導（A13.3）存在的理由正是「程式碼變動時散文沒有理由跟著變」；它涵蓋得了能從程式碼讀出來的宣稱，而這三筆正好是讀不出來的那種。取代它們的每一次都是同一個動作：讓頁面去陳述它能推導出來的東西——用理由取代里程碑、用 build 自己的里程碑取代副本、用標記取代序位——這樣下一次事實改變時，句子會被一起帶著走。

**第 16 到 20 筆是同一種審查方法隔天再跑一次的結果，而第 16 筆是最痛的一筆。** 它就是上面第 15 筆的修法，只活了一天：關於位置的那句話換成了關於標記的那句話，而那個標記在部署上渲染在零列上。*一句過期的宣稱被換成一句從來沒有真過的宣稱*，這更糟，因為這是第二次。原因每次都一樣——跟著修法一起寫的測試斷言的是那段文字，而一段文字自己斷言自己等於什麼都沒檢查。所以這一族的規則現在是明講的，也是從它們身上唯一值得帶走的東西：**一個關於產品的句子，它的測試必須拿渲染出來的頁面去比對程式碼推導出來的值**，絕不能比對那句話本身。為第 16 到 20 筆寫的五支測試都是建一個 store、渲染頁面、再拿輸出跟那個 store 說的話比對——這就是為什麼第 17 筆的端點被斷言成*比它所正當化的那張表更長*而不只是「存在」，也是為什麼第 19 筆的檢查器會先對著我們公布過的文字失敗、再對著取代它的文字通過。

第 7 個值得讀兩次，而且修了兩次。

**第一次修法是改記 response 的 URL** 而非 `page.url`，理由是 response URL 是 redirect chain 的終點、不可能與時序有關。推理健全，前提是假的。事後用瀏覽器實測而非假設：`https://en.wikipedia.org/wiki/Apple_Inc` 回應 **200 且完全沒有 redirect**，網址列大約**兩秒後**才由 MediaWiki 自己的 script 改成 `/wiki/Apple_Inc.`。根本沒有 HTTP 跳轉可記。所以第一次修法會把 gate 釘死在 `/wiki/Apple_Inc`——一個永遠不會與 artifact 相符的 URL——把間歇性失敗變成穩定失敗。

**第一次修法錯在哪，比那個頁面更一般。** 該 gate 拿*一個*凍結的計畫目標比對*一個*記錄端點。只要有東西移動了頁面（301、canonical 改寫），兩者就不相等，於是單一比較只有兩種可用行為：放行所有移動，或擋下所有移動。選哪個 URL 來記錄，就是在選這兩者。那不是修好一個 gate，是把一個巧合換成比較穩的巧合。

**Amendment 26 把它拆成對三個記錄值的兩個斷言**——計畫目標、含每跳狀態碼的完整 redirect chain、以及導覽的落點：

1. **`artifact_source_is_a_url_the_run_reached`** — 主張被驗證所依據的 bytes，來自這個 run 的 trace 能說明它去過的頁面。*證據從哪裡來。*
2. **`landing_explained_from_the_plan_target`** — 該頁面能由計畫目標經一條已記錄的路線抵達：它就是目標本身、或是從目標開始的 redirect chain 終點、或是目標處所提供文件為自己宣告的 canonical URL。*落點是否被說明。*

第三條路線正是 Wikipedia 案例所需、也是任何端點比較無法提供的：當移動發生在回應之後的 script 裡，文件自己的 `rel=canonical` 是唯一不取決於何時讀取的記錄事實。它是一個不可信頁面的主張，所以只在*任務*指名的那個頁面上、且只在 same-origin 內才算數。

**而那條路線是三條中最弱的一條，這件事值得說出來而不是留在程式碼裡。** redirect chain 是一個*觀察*：我們自己的瀏覽器被從一個 URL 送到另一個，並記下每一跳與造成它的狀態碼。canonical link 是*一個頁面對自己的陳述*。DEV-04——這整節在講的那個案例——通過的是第二種。撐住它的不是我們看著 Wikipedia 把我們移走，而是 Wikipedia 說了自己住哪，加上 same-origin 規則界定了那個陳述能伸多遠：一個頁面只能在自己的 origin 內為自己改名，所以敵意站點用它最多只能為它本來就餵給我們的證據作說明。那是一個真實的界線，但它不等於親眼看見移動發生。一份花這麼多篇幅問「什麼條件成立時這個檢查會是在報告巧合」的文件，不能在答案不方便時跳過這個問題——所以：這一條靠的是自我描述；如果那不可接受，誠實的替代方案是讓 DEV-04 判失敗，而不是把規則放寬到它通過為止。

兩個斷言都能單獨失敗，fixture 對每個各有一案，因為一個不可能失敗的斷言正是這張表上一列的缺陷。要緊的是 `/detour`：它 301 到**與 `/moved` 完全相同的頁面**。被送到那裡的 run 是從計畫從未打開的門抵達正確的最終 URL——最終 URL 比較會放行它，而以未被說明的路線抵達正確答案，在這個系統裡計為失敗。

更廣的重點與本節其餘部分相同：一個結果取決於變數何時被讀取的硬 gate 不是 gate，所以它先前每一次通過都比看起來值錢得少——而只讓它不再抖動的修法恢復的是外觀而非 gate。它在 r2 花掉一個案例，而它被發現是因為那個案例在輸入沒變的情況下曾於 r1 通過。

### 5.5 唯一一次操作失誤，以及系統對它做了什麼

以上都是程式缺陷。這一則是人在線上系統上犯的錯，記在這裡是因為對它的反應是本文中設計有效的最佳證據。

**發生了什麼。** product owner 啟動計分輪次 `r2` 並宣告了。四分鐘後 engineering session 推了一個 commit。在這台 host 上，推到 `master` **就是**部署（Amendment 20），於是計分中的容器在一輪付費計分進行時被換掉。這完全不是安排、模擬或刻意觸發的；engineering session 被告知輪次開始了，然後還是推了。

**系統做了什麼。**

- **dev split 已跨過邊界**，以乾淨名稱 `dev-deploy-aa1ee6c5d5eb-r2.json` 寫出，裡面帶著它跑的 commit。它是有效的量測，也被當成有效量測使用。
- **experimental split 中途被打斷**，留下 `eval-results/.rounds/r2-experimental.inflight.json`，而該工作負載的下一次啟動**拒絕重跑那個 split**，而不是靜悄悄再花一次錢——操作者必須讀 log 並自己決定，那正是這個標記的全部意義。
- 沒有任何東西被寫成日後會被讀成「已完成輪次」的名字，也沒有任何部分結果被聚合進任何地方。

**為什麼放在正文。** 一長串修訂在論證這個行為（推送即部署、輪次鎖在啟動時的 build、被打斷的付費 split 必須 fail-closed），而這是它第一次由真實錯誤而非測試觸發。損失的那一輪已計入 ledger。

修正是程序性而非技術性的：其餘輪次在凍結 commit 上執行、中間不推送，而 test split **單獨執行**，不與可能被打斷的 split 共用一輪——held-out 的第一次執行不能有第二次。

**Mutation 結果，如實出貨。** fixture 宣告了一份 mutation 目錄，實際接線的是**兩個**：`mu2-text`（locator 底下的控制項與 label 文字被改）與 `mu6-overlay`（一條蓋住 pager 並吞掉點擊的橫幅）。兩者都能從前端以 `seed` 指令觸及，也都在我們自己的 fixture 上展示——這正是它們被發布為 *mechanism evidence*、不計入任何成功率的原因：在自己寫的站點上量修復率，就是自己改自己的考卷。

MU-4/5/7/9 與完整 sweep 被**砍掉**（Amendment 25）：兩個可用 mutation 加一個 healing 展示是證據，九個是研究計畫。

**寫回與 healing 展示。** 展示 A14.6 對**逐位元組封存的真實 books.toscrape Nonfiction 列表頁**、以及 pager 被以改版方式重寫的副本（新 class、新 wrapper、新增 `data-` hook，accessible name 不動）各跑一次：`li.next a`（我們的拼法）撐不過去，*名稱為 "next" 的連結*（頁面自己的拼法）撐得過去。驗證在 `tests/test_healing_demonstration.py`。

比讀起來更弱的部分：這個展示是一個頁面、一種 mutation 形狀，而 memory 是在 locator 已停止解析時才介入，不是第一選擇。更重要的是：**至今沒有任何已 commit 結果檔中的 run 被記錄產生過真正的跨族策略轉換**（A-11）。機制建好了、被測試套件操練過，但它的實地證據是一個展示而非一個比率。一個我們有信心、卻指不出任何生產實例的機制，正是這份報告應該讓人不舒服的那類主張。

### 5.6 Silent failure——我們真正在意的指標

大聲的失敗很便宜：run 說出它做不到什麼，讀者相信它。silent failure 是一個貌似合理的錯答案，是唯一真正傷害使用者的結果。

**採用的定義**：回傳貌似合理的答案、標記為成功、但那不是所問問題的答案——包含從錯的頁面讀到看起來正確的值、沒有證明就斷定不存在、以及把部分答案當成完整答案呈現。

**橫跨每個已 commit split 的計數：零個 run 以 silent failure 的形式被釋出。** 這個數字本身意義很小，所以以下是它背後的支撐與它最弱的地方。

*如果發生了，怎麼會被偵測到。* 四個獨立機制，每一個在開發期間都真的對真實 run 觸發過：

1. **artifact 來源對照任務自己的字。** 一個在任務指名 Wikipedia 時卻回答我們 fixture 的 run，被「比對 artifact 來源與任務指名站點」抓到——由 verifier 讀，不是由 router 讀。
2. **凍結參數比對。** 一個要求依 *CIK ascending* 排序的任務被塞了現成的 *GICS Sector descending* 計畫，完美執行後回傳 `succeeded_verified`。所有結構性檢查都通過，因為每個結構性檢查比的都是「run 對計畫」，而沒有人比過「計畫對任務」。當時有四個 dev 案例是這樣被回答的。計畫的凍結輸入現在會對照任務自己的字檢查。
3. **不存在需要正面證據。** `no_result_verified` 需要定位到 empty-state 元素，或涵蓋整個結果集的 coverage anchor；沒有就棄權——這是 L-3，而且它讓我們實際損失分數。
4. **`app/suspicion.py` 對照 reduction log 稽核安靜的結果。** 由*我們自己*的頁面縮減丟掉元素所造成的棄權，看起來與誠實的棄權一模一樣，所以每個安靜的結果都會對照 reducer 移除了什麼做檢查，兩者對得上就標記。

*這個零最弱在哪，直說。* §5.3 就是極限：OP-4 與 OP-5 上沒有獨立 oracle 推導正確答案，所以這兩筆記錄上的 silent failure 只能靠產品自己的 verifier 抓——而那正是被檢查的對象。機制 4 也只涵蓋我們想得到要看的東西；由我們沒有對策的原因造成的棄權，與正確的棄權無從區分。**一個由無法登記該事件的儀器產生的零不是結果**，而在我們最強的兩筆記錄上，那個儀器部分失明。

*把線上系統當對手來跑（而非讀程式碼）找到了什麼*：一個線上的 `succeeded_verified`，任務要的是 *"UPC and availability"*，它凍結了一個未命名的主張、驗證了 UPC、然後靜靜丟掉 availability。依上面的定義那就是 silent failure，而且是在 split 都評分完之後才發現的、不是被 split 發現的。修法是要求「有 *n* 個被詢問部分的任務必須產生 *n* 個主張，否則回 `partial`」——這也是本文中最清楚的證據：你自己寫的 split 量不到陌生人任務所落到的表面。

**對我們自己的流程 finding。** 最後八條 spec 修訂中有六條處理的是量測儀器（ledger、預算上限、評估 provenance、spec 自己的變更紀律），而不是產品能做什麼。產生那些修訂的直覺，與找出 §5.4 中七個壞掉檢查的是同一個直覺，也真的是本庫最有價值的東西。但它同時變成了失敗模式：在它稽核儀器的時候，沒有人稽核承諾，於是一條假的限制與一份誇大記錄的支援矩陣雙雙活到線上部署。修正方式是把線上系統當成對手來跑，而不是讀程式碼。
