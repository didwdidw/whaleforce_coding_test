# 給評分者：操作說明，以及邊操作邊講的實作說明

**線上系統：<https://wf-agent.zeabur.app>**

這份文件同時是**操作手冊**和**說明報告**。我們不假設你會翻我們的工程規格，所以每一步先告訴你按什麼、會看到什麼，緊接著用同樣的篇幅說明：這一步系統實際在做什麼、做得好的地方我們是怎麼做到的、還不夠好的地方為什麼還不夠好、以及我們已經試過什麼。

**先講結論。** 這是一個瀏覽器自動化代理，設計目標只有一個：**寧可沒有答案，也不要一個看起來合理但是錯的答案**。它接受英文的自然語言任務，用真實瀏覽器去做，然後回傳「一個附帶證據的答案」或「一個說清楚自己做不到什麼的失敗狀態」。核心手法是：**模型只負責提出答案，答案能不能算數，由決定性的程式碼回到當時保存下來的頁面位元組裡重新找一次來決定。**

我們也用一組從來沒被開發過程看過的題目量過它，結果比我們自己出的題目差很多。那個落差寫在後面，沒有被藏起來。

### 花多少錢、多久，以及撞到上限會看到什麼

先講這個，因為它會發生在你心裡打分的那一刻，而且很容易被讀成「系統壞了」。

- **拒絕型任務**（沒指名頁面、要登入、要付款）：**0 元、約 0.02 秒**，不呼叫模型。
- **模型執行的任務**：中位數約 **USD 0.002**、**5～15 秒**。
- **限制**：同時 2 筆、佇列 2 筆、每個 session 10 次、每日上限 USD 0.5。

撞到任何一條，你會看到 `blocked / queue_full`、`blocked / session_quota` 或 `blocked / provider_quota`，並附 `HTTP 429` 和 `Retry-After`。**那些是宣告過的狀態，不是故障**——`/coverage` 頁面上就列著它們。

## 步驟 1：打開網站，先不要急著送任務

**你要做的：** 開 <https://wf-agent.zeabur.app>，直接捲到下面的 Runs 表格，隨便點一筆進去。

**你會看到：** 十幾筆已經跑完的執行紀錄，包含成功的、證明「查無此物」的、被拒絕的、以及各種失敗的。其中一批是容器每次啟動時就自動跑好的，其餘是真人送出的。

### 這一步在做什麼

這幾筆是**預先執行**的，跑在我們自己寫的測試站上，而且走的是不需要模型的路徑。它們存在的理由有兩個，都是刻意的：

1. **冷啟動。** 這個部署平台的容器會被回收，第一個請求可能要等。一個評分者的第一印象不應該是一個轉圈圈的畫面，所以首頁一定有東西可以立刻點開看。
2. **沒有模型金鑰也能看到系統在做事。** 這些紀錄裡有真實的瀏覽器操作、真實的頁面存檔、以及驗證器的判定，全程沒有呼叫任何模型。

### 這一步我們做得還可以，怎麼做到的

開機執行的那一批，它們的證據是**釘住的**——不會因為過期或磁碟壓力被清掉。你可以在 `/healthz` 的 `storage.artifacts_pinned` 看到這個數字，旁邊的 `note` 直接寫著為什麼：**一個示範不該假裝自己是即時的，所以它的位元組要能一直被打開。**

一個誠實的提醒：Runs 表格是**同一段任務文字只留最新一筆**。所以只要有人（包含你）重跑了一個示範任務，那筆開機執行的列就會被你的新執行取代。**表格是最近發生了什麼，不是完整清單。** 這個去重是為了避免整個首頁被重複的量測探針洗版，但它的代價就是示範列會被擠掉。

### 這一步還弱在哪

冷啟動本身我們沒有花錢去避免（例如保溫）。我們量到的是：一次部署到可用大約兩到三分鐘，但**對一個正在使用的人來說，中斷只有十幾二十秒**。我們選擇接受它，用上面那個設計去繞過去，而不是付錢買一個常駐實例。

## 步驟 2：輸入一個任務

**你要做的：** 在輸入框打一個英文任務。這兩個可以直接複製：

```
Go to the nonfiction category listing on books.toscrape.com and read the second page of results
```

```
Open the product detail page for A Light in the Attic and read its labelled product information
```

**你會看到：** 送出後跳到該筆執行的頁面，開始跑。

### 兩條規則，以及為什麼

**規則一：建議用英文，但中文不是壞掉的。** 四項承諾的中文措辭**路由層認得**——我們實測過這一句：

```
在維基百科的 List of S&P 500 companies 條目上，把成分股表格依 GICS Sector 遞減排序，並告訴我第一列
```

它拿到 `T-DECLARED` + `succeeded_verified`，2/2 宣稱通過獨立重解析，答案與英文版一致。拒絕規則也一樣有效（要求登入、要付款的中文任務照樣被擋）。

**沒有被翻譯的是那些必須對上頁面文字的值**——欄位標題、分類名稱、商品欄位標籤。那些請照頁面上的拼寫寫（像上面那句裡的 `GICS Sector`）。

**我們沒有把中文納入公布的成功率**，因為我們的評測集全是英文。所以：能用，但那個數字不涵蓋它。**一個沒有被量過的承諾不是承諾。**

**規則二：必須指名網站或頁面。** 這個不行：

```
In the S&P 500 constituents table on Wikipedia, sort by CIK ascending and tell me which company is first.
```

這個可以：

```
On the Wikipedia list of S&P 500 companies, sort the constituents table by GICS Sector descending and tell me the top row
```

### 這一步在做什麼

第一個講法只是**描述**了一個頁面，沒有**指名**它。系統會在開始瀏覽之前就停下來，告訴你它沒有起點，並請你給一個網址或條目名稱。

### 為什麼這是刻意的，不是做不到

我們當然做得到「拿去搜尋，挑第一個結果」。問題是：**挑一個任務從來沒指名的起始頁，等於去回答一個沒有人問過的問題。** 如果搜尋結果挑錯了條目，後面每一個檢查都會通過——因為所有結構性檢查比對的是「執行有沒有照計畫做」，而不是「計畫是不是這個任務要的」。這正是這個系統最想避免的那種失敗：**看起來完全正常，而且是錯的。**

我們在開發中真的踩過這個坑：一個要求「依 CIK 遞增排序」的任務，被配到一份「依 GICS Sector 遞減排序」的既有計畫，執行得完美無缺、回報成功，每一項結構檢查都通過——因為沒有人拿計畫去比對任務本身的字句。修法是把計畫凍結下來的參數拿去跟任務原文對照。

### 這一步還弱在哪

**這條規則會擋掉很多看起來很普通的問題。** 在完全沒看過的題組裡，八題有兩題就是因為沒指名頁面而在瀏覽前被拒。這是真實的可用性成本，我們選擇付它，因為另一個方向的成本是靜默的錯答。

## 步驟 3：送出前就會看到的分層標籤

**你會看到：** 結果頁最上面有一個標籤，三種之一。

| 標籤 | 意思 | 算進我們公布的成功率嗎 |
|---|---|---|
| `T-DECLARED` | 這題落在我們**明確承諾過**的能力範圍 | **會** |
| `T-EXPERIMENTAL` | 其他任何公開、可讀、政策上乾淨的網站。盡力而為，**棄權是正確結果** | 不會，另外分開報 |
| `T-REFUSED` | 違反政策（要登入、要付款、要寫入），**在任何瀏覽發生前**就拒絕 | 不適用 |

### 這一步在做什麼

分層在**執行開始之前**就決定，而且會顯示在表單、結果和 API 回應上。這是為了讓「你到底承諾了什麼」變成一個看得見的東西，而不是一句話。

### 我們承諾的是四項，而且是「網站 × 操作」，不是「網站」

我們承諾的不是「我們支援維基百科」。**知道怎麼排序維基百科上的表格，完全不代表知道怎麼展開維基百科上的摺疊區塊。** 那是兩件事，各自要有各自的證據。所以承諾寫成四項：

| 網站 | 操作 | 為什麼這件事不容易 |
|---|---|---|
| 維基百科 | 把可排序表格依指定欄位排序，讀出新的第一列 | 排序是前端做的：DOM 順序變了，網址沒變，所以**這個答案沒辦法靠抓網址拿到** |
| 維基百科 | 展開摺疊的區塊，讀出展開前看不到的值 | 那個值在真的互動發生之前，根本不在頁面的可見狀態裡 |
| books.toscrape.com | 走分類、翻頁、取出清單層級的事實 | 跨頁狀態，而且誠實的答案常常需要先證明「我看完了」 |
| books.toscrape.com | 打開商品頁，取出**具名欄位**（例如 UPC、庫存、未稅價） | 答案是一個「標籤 → 值」的綁定，不是「頁面上剛好出現的一個字串」 |

我們原本承諾七項，後來**主動砍到四項**：另外三項是跑在我們自己寫的測試站上的。**在自己寫的網站上量自己的可靠度，等於自己出考卷給自己考。** 那三項還在，但它們被標成「機制證據」，不進任何成功率。

**四項都可以直接貼上去自己跑**（第一項在步驟 2 已經給過）：

```
On the Wikipedia article for Apple Inc., expand the first collapsed box at the foot of the page and tell me its title and the label of its first row group.
```

```
Go to the nonfiction category listing on books.toscrape.com and read the second page of results
```

```
On books.toscrape.com, open A Light in the Attic and tell me its UPC.
```

第二項（展開摺疊區塊）特別值得跑一次：它成功時會產生一個叫 `still_collapsed` 的宣稱，值是「展開後那個摺疊標記**不見了**」。**那是一個對「狀態真的變過」的檢查，不是對「值長得對」的檢查**——這正是抓網址拿不到的東西。

首頁那顆寫著 `Expand the collapsed navbox on that article` 的示範按鈕**一定會被拒**（它用「那個條目」指涉上一句，沒有指名頁面，剛好撞上規則二）。那顆按鈕是一個示範缺口，不是這項能力的缺口——請用上面那句。

### 這一步還弱在哪 —— 這是最需要你知道的一條

**分層路由認得的句型，比上面這張表承諾的窄。**

在完全沒看過的題組裡，出題者標為承諾層的四題，**有兩題被系統路由到 `T-EXPERIMENTAL`**——它們根本沒走到承諾的表面上。

為什麼還有這個問題：我們承諾的單位是「網站 × 操作」，但實作認得的是**一組比較窄的措辭**。我們自己出的題目量不到這件事，因為那些題目是由已經知道系統吃什麼句型的人寫的。

我們已經試過什麼：我們在凍結前抓到並修好了同一族的另一個實例——商品頁那一項原本被寫死成單一本書，所以問任何其他書都會掉到實驗層。那是同樣的病：**承諾寫對了，實作做窄了。** 修完之後我們才發現，路由層還有一個更上游的版本，而那個是完全沒看過的題組替我們找出來的。時間不夠再修一輪，所以我們把它寫在承諾旁邊，而不是留給你自己踩。

**請把上面那張表理解成：以任務的措辭符合我們預期為前提。**

## 步驟 4：執行中，系統在做什麼

**你會看到：** 頁面上一步一步跳出進度。承諾層的任務中位數大約 6 秒，實驗層大約 12 秒。

這中間依序發生四件事：

**一、把目標凍結成一個可檢查的條件。** 在瀏覽器打開之前，任務會被編譯成一組「要滿足什麼才算答完」的條件，加上「哪些介面動作必須真的發生過」，然後**做雜湊、凍結，下游不能改**。

> 為什麼要凍結：另一種做法是「看到頁面之後再決定什麼算成功」，那正是一個代理說服自己接受一個答案的過程。凍結的代價是**我們可能因為問錯問題而失敗，而且那個失敗會被看見**，不會被吸收掉。

**二、政策閘門，在任何導航之前跑。** `robots.txt` 是**執行**而不是參考的——我們自己實作了一套符合標準的比對，並且有獨立的持續整合工作在測它，因為**一個微妙地寫錯的政策檢查，比沒有政策檢查更糟**。同時，每一次跳轉都會重新解析並檢查目標 IP，內網、回環、連結本地位址一律拒絕。

**三、真的用瀏覽器操作真的頁面。** 不是抓網址、不是解析 API。承諾的那些操作之所以難，就是因為它們的答案不存在於任何一個可以直接抓的網址裡。

**四、每一個重要的頁面狀態都被存下來。** 完整的 DOM、文字、螢幕截圖，以內容雜湊定址。

### 這一步還弱在哪

**每次執行都有步數上限，而且是 fail-closed 的。** 用完就結束，**不給答案**。你可以自己重現：

```
How many books are listed on the last page of the Nonfiction category on books.toscrape.com?
```

「最後一頁」要靠一直翻頁翻到下一頁按鈕消失為止，那個分類長到會先撞上上限。我們**刻意不讓它把「剛好翻到的那一頁」當成最後一頁回報**——那正是這個系統存在的意義。這條限制我們留著沒改，因為改它的方向只有兩個：放寬上限（花更多錢、更久，而且只是把界線往後推），或是允許它猜（不可接受）。

## 步驟 5：結果出來 —— 這是整個系統的核心

**你會看到：** 一個狀態、一段說明，以及（如果有答案的話）每一個值旁邊都掛著它的證據。

### 這一步在做什麼

模型看完頁面之後，會提出一個答案。**那個提議被當成假設，不是結論。**

接著，決定性的程式碼會做這件事：**回到當時存下來的那份頁面位元組裡，重新去找那個值一次**，而且必須是**透過任務指名的那個標籤**找到的。找不到，這次執行就不算成功——不管模型多有把握。

一句話：**模型提議，決定性程式碼裁決；而裁決的對象是保存下來的位元組，不是即時的頁面。**

### 為什麼一定要對「保存下來的位元組」而不是「即時頁面」

這是整份設計裡最重要的一個決定，值得多講兩句。

如果回頭去打即時頁面來驗證，你會得到另一種失敗：**頁面在這中間變了，檢查通過了，而這兩件事毫無關係。** 你以為你驗證了答案，其實你只是驗證了「現在的頁面上有這個字串」。

對存下來的位元組驗證，換到的是三個性質：

1. **第三方可以重跑。** 存檔以內容雜湊定址，而且公開可取。任何人都可以拿同一份位元組，自己重跑一次驗證。
2. **不受頁面漂移影響。** 執行之後頁面怎麼變，都不可能把一個沒過的檢查變成過的。
3. **不可能靠巧合滿足。** 值必須從任務指名的**標籤**結構性地連過去。「頁面上某處剛好出現這個字串」不算答案——那是子字串搜尋，不是「這個商品的 UPC 是多少」。

### 我們也對「不存在」設了同樣高的標準

「我找了，沒找到」**不構成**「沒有東西符合」。要回報「查無此物」，系統必須拿出正面的證明：要嘛真的定位到頁面上的「無結果」元素，要嘛證明整個結果集都被讀過了。做不到就棄權。

### 這一步還弱在哪

**驗證器檢查的是「這個宣稱和我們保存的證據一致」，不是「這個宣稱在世界上為真」。** 這兩件事不一樣，頁面上寫得很清楚。

在我們自己的評測裡，四項承諾中**只有一項**有辦法**獨立推導出正確答案**再去比對——就是表格排序那一項：我們的評測工具自己去抓那篇條目、自己判斷該用數值還是字典序（這個判斷本身就是陷阱：同一欄用兩種排法會得到不同的第一列，而且兩種看起來都很合理）、自己排一次、比對第一列。**另外三項沒有獨立的正確答案來源**，特別是展開摺疊區塊那一項——那個狀態只有在互動發生之後才存在，任何直接抓取都會跟一次正確的執行對不上。

所以我們公布「沒有出現過『通過驗證但其實是錯的』」這句話的時候，同時公布它的邊界：**在那三項上，這個保證靠的是我們自己的檢查器，而那正是被檢查的東西。**

我們已經試過什麼：我們一度在評測題目上寫著每一題都有獨立的正確答案來源——**那是假的，程式從來沒有實作過。** 這件事是我們自己審查時抓到的，而且它是我們找到的所有缺陷裡，**第一個方向是「讓沒被證明的東西看起來被證明了」的**。修法是真的把表格排序那一項的獨立推導做出來，然後把其他每一題的欄位改寫成「這一題實際上被什麼檢查」，三選一：獨立推導、證據重查、軌跡檢視。

### 這一頁有一個我們特別想請你看的東西

**「不乾淨的安靜結果」徽章。**

一個棄權和一個正確的棄權，長得一模一樣。問題是：如果是**我們自己**在把頁面壓縮送給模型的時候，把那個元素丟掉了，那模型誠實地說「我看不到」，就會由一個其實有答案的頁面產生。

所以每一個安靜的結果（棄權、查無此物）都會被拿去跟「我們自己刪掉了什麼」對照一次，對得上就掛徽章。

**這個部署上正好有一筆掛著它**，十秒就能看到——首頁 Runs 表格裡 MDN 那一列（`developer.mozilla.org … Array/flat` 的相容性表格，步驟 8 的第三個例子），點進去，標題列有一個紅色的 `not a clean unsupported`。

**一個描述得出來、卻找不到實例的機制，在讀者眼裡等於沒有**，所以我們直接把實例指給你。

### 這一步還弱在哪

**那個稽核只涵蓋我們想到要去看的東西。** 一個由我們沒有計數器的原因造成的棄權，跟一個正確的棄權，在我們的儀器上是分不出來的。這一條寫在頁面上，也寫在報告裡。

## 步驟 7：讀懂結果

**七種最終狀態，這是完整的一份，不會有第八種：**

| 狀態 | 意思 | 算成功？ |
|---|---|---|
| `succeeded_verified` | 有答案，而且答案被程式從存檔裡重新讀出來比對過了 | ✅ |
| `no_result_verified` | **證明了「沒有」**——找到無結果元素，或證明整個結果集都讀過了 | ✅ |
| `partial` | 只滿足了一部分驗收條件 | ❌ |
| `unverified` | 有讀到東西，但無法證明它成立（例如涵蓋範圍沒證明） | ❌ |
| `unsupported` | 這件事這個版本做不到，看過之後誠實棄權（或瀏覽前就說沒有起點） | ❌ |
| `blocked` | **有東西擋住我們**——robots 禁止、HTTP 401/403/429、佇列滿了 | ❌ |
| `failed` | 真的失敗——步數或時間用完、必要動作被跳過、驗證對不上 | ❌ |

### 一條規則請直接記住

**`partial` 和 `unverified` 永遠不會被當成成功。** 它們看起來像「差不多有做到」，但在這個系統的定義裡，它們跟 `failed` 一樣不進成功率、不會被聚合、不會在任何地方被描述成成功。

首頁的 Runs 表格有一個獨立的 `Counts as success` 欄位，逐列列出 yes / no。**請看那一欄，不要從狀態字面自己推斷。** 在單筆執行的詳情頁上，同一件事由標題列的徽章承擔：不算成功的會多掛一個 `does not count as success`。

### 這件事為什麼做得到

因為狀態和失敗原因都是**封閉集合**——七種狀態、十八種失敗原因，要新增只能透過一次書面修訂。**一個「絕不把部分結果講成成功」的保證，只有在集合封閉、規則是機械式的時候才有意義**；如果狀態可以隨手新增，那句保證就只是一句話。

## 步驟 8：去看失敗 —— 這頁可能是最值得看的

**你要做的：** 打開 <https://wf-agent.zeabur.app/support>，捲到「Known limitations you can reproduce」。

**你會看到：** 一排限制，但**每一條都不是散文**——每一條都是**一個你可以直接打進輸入框的任務**，加上它會產生什麼結果、以及為什麼。

幾個可以直接複製：

```
Is there any book in the Fiction category on books.toscrape.com priced over £50?
```
→ 讀到 65 筆中的 20 筆，回報涵蓋範圍**未證明**（`unverified`）。多頁的分類橫跨多份存檔，而這個版本只對一份驗證。單頁的分類（Poetry、Travel）會被證明並回答。

```
Use Wikipedia's search page to find articles mentioning 'convertible arbitrage'.
```
→ 導航前就拒絕（`blocked`），並把 robots 規則原文引出來。維基百科不允許那條搜尋路徑。**這個拒絕是對的，而它同時也是一條限制**：一個很普通的問題，如果唯一的路線被禁止，在這裡就沒有答案。

```
On developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/flat, tell me the Chrome version listed in the browser compatibility table.
```
→ 真的去瀏覽了，然後棄權（`unsupported`），並指名它停在哪一步、哪一頁、哪一部分條件沒滿足。**它不會亂猜一個版本號。** 那個值坐在一個相容性表格裡，它的「標籤」是一個圖示加上欄位位置，不是文字，所以沒有東西可以讓程式重新讀一次。

### 這一步在做什麼，以及為什麼我們認為它值得你花時間

**這份清單裡的每一條，都是對線上系統實際執行過、把觀察到的結果記下來的**，不是憑印象寫的。我們另外寫了一支程式，會把整份清單（包含清單自己聲稱的「這樣改寫就會成功」的講法）拿去對部署跑一遍。

**第一次跑那支程式的時候，七條裡有四條沒辦法照著寫的方式重現。**

- 一條聲稱「把條目名稱補上就會成功」——**它從來沒成功過**，三十秒就能重現。
- 一條寫的失敗原因分類是錯的，實際跑出來的那個更精確。
- 兩條是**系統已經變好了，而文件爛在原地**：其中一個任務已經開始成功，另一個已經真的能證明「不存在」了。

**發表一個已經不會發生的棄權，跟發表一個從來沒work過的補救講法，是同一種缺陷。** 這也是為什麼我們堅持限制清單必須是可執行的：它可以被推翻，所以有人會發現。

順便，那次執行還抓到一個沒有任何測試抓到的回歸：一種頁面擷取動作佔用了自己的一格步數預算，導致擷取比較多的執行只剩下一半的可用步數。

### 一個實用提醒（你明天很可能會遇到）

如果你在 books.toscrape.com 上看到 `blocked / robots_disallowed`，**請先打開軌跡再下結論**：

- `source: "matched"`（旁邊會附上命中的 `rule` / `pattern` 原文）→ 站方**真的**禁止。維基百科的 `Disallow: /wiki/Special:` 就是這種。
- `source: "unfetchable"`（或 `unparseable`）→ **我們**讀不到那份規則，所以保守拒絕。

books.toscrape.com **根本不發布** `robots.txt`：正常情況會回 404，我們讀成「不受限」並放行。所以在那個站看到 `robots_disallowed` 幾乎一定是 `unfetchable`——也就是**當下抓 robots.txt 的網路問題**，不是站方禁止。重跑一次通常就好。

這不是假設。這件事在我們那組完全沒看過的題目上發生了三次，而且我們一開始把它讀錯了——詳見最後一節。

## 步驟 9：另外兩頁

**`/coverage`** — 這個部署實際上產生過哪些結果狀態。它的用途是讓你分辨「這個狀態我們宣告了但從來沒有任何程式路徑到得了」跟「這個狀態真的發生過」。舉例來說，注入偵測是一個我們宣告了、但**目前沒有任何程式路徑會到達**的狀態，這頁把它標成**「未建」並附上理由**，那一列的「Due at」是一個破折號：它不帶任何未來時程，也**永遠不會被算成逾期**。被砍掉的工作顯示成「排程中、還沒輪到」，等於宣告一個我們不打算兌現的計畫，而這一頁正好是最不該樂觀的地方。

你在頁首多半會看到那個總結徽章是**沒有通過**的，後面掛著十種從未被產生過的失敗原因（例如佇列滿了、逾時、供應商錯誤）。**那是誠實的讀數，不是缺陷**：這些原因在這個部署上真的一次都沒發生過，而這一頁的工作就是說出來，而不是替它們找理由。其中兩種你可以自己觸發（見步驟 8 與併發限制），觸發之後那個徽章就會少掉一項。

這份帳本記在持久磁碟上，所以它是**跨部署累計**的，不會因為重啟或重新部署歸零。（這一頁上有兩句自述說它會歸零，那兩句是錯的，寫在最後一節的已知缺陷裡。）

**`/healthz`** — 運行狀態的 JSON：目前跑幾筆、佇列多深、瀏覽器記憶體、存檔用了多少空間、離上限多遠、以及自我維護記憶體的計數器。

**三個欄位最容易被讀反，先講：**

1. **自我維護記憶體的計數器多半會是「有存、但一次都沒被查詢」**（存了幾筆定位方式，命中、使用、修復全是 0）。**這正是一個健康的部署該有的樣子**：記憶體只在某個定位方式**失效**時才會被叫出來，所以只要頁面沒改版，這些數字就不該動。這一頁會把這句話直接寫在計數器旁邊，因為一個裸露的 0 讀起來像「這機制做了但是死的」。

2. **憑證政策**（`credentials.policy`）可能是兩種之一：計分期間用的是**只用免費額度**的政策，計分結束後公開站切成**免費額度優先、被限流或用完時自動 fallback 到付費金鑰**的政策。**請以你當下看到的那一欄為準**——這一頁會直接說出現在生效的是哪一個、以及哪些層級在該政策下可用。

3. **`provider_spend` 上的數字，跟我們公布的開發總花費對不起來，那是對的。** 這一頁的 `cumulative_billed_usd` 很可能是 **0**，而下面「數字一覽」寫的是 USD 0.1515。原因是**兩個行程各記各的帳**：那 0.1515 花在一個持有付費金鑰、專門跑計分題組的服務上，公開站是另一個服務，讀不到它的帳本。同一個欄位旁邊的 `notional` 是「如果這些呼叫全部走付費計價會是多少」，`billed` 是「實際被收費多少」——免費額度內的呼叫兩者會差開。這一頁的 `provider_spend.meaning` 欄位就是在解釋這件事。

## 做得好的地方，以及我們具體怎麼做到的

**一、證據優先的驗證。** 上面步驟 5 講的那件事，是整個系統的地基：條件在瀏覽器打開之前凍結並雜湊，模型只提議，決定性程式碼回到保存的位元組裡重新解析，而且必須經過任務指名的標籤。這讓「驗證」變成一件第三方可以自己重跑的事，而不是一句我們自己說了算的話。

**二、承諾寫成「網站 × 操作」，並且附上量到的數字。** 宣稱「我們能處理任何網站」很容易，而且無法被否證。**宣稱四項具體操作、在我們不控制的網站上、附上量測數字和信賴區間，是同一句話的可否證版本。** 代價是我們公布的成功率覆蓋的表面，比一個講得更含糊的產品小很多——而且在我們把自己寫的測試站那三項撤下來之後，它又變得更小了。

**三、失敗帶著具體的原因，而不是一個籠統的錯誤。** 七種狀態 × 十八種原因，都是封閉集合。一個失敗的執行會告訴你它停在哪一步、哪一頁、哪一部分條件沒滿足。**「這一步丟了例外」不是一個診斷。**

**四、「不存在」必須要有正面證明。** 這條讓我們在評測上實實在在丟掉分數（多頁分類的問題會棄權而不是回答），我們留著它。

**五、重試和真正的策略切換被分得很開。** 同一個策略再跑一次叫**重試**，會被記錄成重試——**它不是自我修正**，把它算成自我修正是造假這項要求最容易的方法。真正的**策略切換**是換到另一個策略家族（無障礙樹 → 文字錨定 → 結構 → 替代路線 → 替代表徵），而且必須由一個**具名的、被診斷出來的原因**觸發，原因來自一個封閉集合。詳情頁上兩個數字是分開列的。

**六、自我維護的記憶體，只從「驗證通過」的執行學習。** 它記的是元素的身分，**從來不記值**，所以記憶體裡的東西不可能變成一個答案。而且一個被記住的定位器，會像其他任何定位器一樣被重新解析、重新驗證——**記憶體省的是搜尋的力氣，永遠不是證明。** 連續失敗三次會被隔離，超過確認期會失效，計數器公開在 `/healthz`。

**七、拒絕用螢幕座標點擊。** 這是最後一種手段，我們在規劃階段就把它擋掉了。盲目點座標會產生的，正是這個產品存在要防的那種失敗。

**八、頁面上的文字一律當成不可信資料。** 網頁上的字永遠不能改變目標、分層、政策、預算或記憶體。這是**結構上**做到的（記憶體只餵給定位器解析，從來不會被當成自由格式的指令注入給規劃器），而不是靠拜託模型。

| 開發用（自建） | 我們 | 計入通過率的 11 題中通過 **10 題** |
| 實驗用（從沒碰過的網站） | 我們 | 通過驗證 **3/10**，95% 信賴區間 **0.11–0.60** |
| **保留題組（開發過程從未看過）** | 產品負責人，工程端全程沒看過 | **1/8**，95% 區間 **0.02–0.47**；承諾層 4 題中 **1 題**，區間 0.05–0.70 |

**這個落差本身就是結論，不是註腳。** 只跑一次，跑壞了也不重跑——第一次跑出來的就是分數。

**那八題裡有五題從來沒有開始瀏覽。** 而這五題要拆成兩半，因為它們的性質完全不同：

- **三題是一次 `robots.txt` 取得逾時。** 同一個網站、同一個原因：我們讀不到那份規則，所以保守拒絕。**那不是政策覆蓋面的發現，是一次可用性事件**——那個網站根本不發布 `robots.txt`，而且在那之前二十分鐘的另一輪計分裡，同一個網站的七題全部正常瀏覽。
- **兩題是任務沒有指名頁面。** 這個是真的，就是步驟 2 講的那條刻意的限制。

所以那 1/8 是一個**下限**，而且它量到的「可用性」成分不亞於「能力」成分。**但它仍然是分數**，我們不重跑。

### 二、我們一開始把上面那三題讀錯了，而且錯得很典型

**我們最初的結論是「這三題證明我們對『一般任務』的直覺比我們自己的政策寬」。那是錯的。**

那個結論是**看著失敗原因的統計圖表下的判斷，在打開任何一筆執行紀錄之前**。它之所以能活下來，是因為那一輪的摘要裡沒有任何東西可以反駁它——摘要的精確度取決於失敗原因分類的精確度，而那個分類不夠精確：**同一個標籤同時承載「站方禁止我們」和「我們讀不到站方的規則」兩件事。** 兩種拒絕都是對的，但只有一個標籤是對的。

**打破它的是點了一個連結。** 打開那三筆的執行紀錄，看到的不是規則，是一行逾時錯誤。

我們把這件事完整寫進報告裡，指名道姓，因為：這份提交裡其他所有的缺陷，都是「一個檢查回報了一個巧合」。**這一筆是我們自己，在最後一天，做了大型語言模型會做的事：產出一個貌似合理、而摘要無法否證的結論。** 抓到它的機制，是我們一小時前才手動搶救出來、剛發佈上線的那批證據。

**為什麼還沒修：** 把那個標籤拆成兩個，會改變一個已經被計分結果報導過的分類。在死線前一天做這件事，換來的風險大於收益。我們選擇留著缺陷、寫清楚它，並在 `/support` 和上面步驟 8 教你怎麼分辨。

### 三、分層路由認得的句型比承諾窄

見步驟 3。承諾層四題有兩題沒走到承諾的表面。**我們自己的題目量不到這件事**，因為那些題目是知道系統吃什麼句型的人寫的。同一族的上游版本我們在凍結前修掉了一個（商品頁被寫死成單一本書），但路由層這個更上游的版本，是保留題組替我們找出來的，來不及再修一輪。

### 四、四項承諾裡，有三項沒有獨立的正確答案來源

見步驟 5。只有表格排序那一項，我們的評測工具可以自己推導出正確答案再比對——而且在最後一輪計分裡它真的跑了，八個儲存格全部一致。**另外三項的正確性，靠的是我們自己的驗證器**，而那正是被檢查的東西。這一條我們選擇公開承認，而不是讓那句「沒有出現過通過驗證但其實是錯的」不加限定地站在那裡。

**一個無法登記某件事發生的儀器，量出來的零不是零，是沒有資訊。**

### 五、多頁的涵蓋範圍證明不了，所以那些問題會棄權

跨越多頁的分類會跨越多份存檔，而這個版本對一份存檔驗證。單頁的分類會被證明並回答，多頁的會被回報成「未證明」而不是拿我們剛好看到的那一頁去回答。這是「不存在必須有正面證明」那條規則直接的代價，我們留著它。

### 六、步數上限會讓長翻頁任務沒有答案

見步驟 4。fail-closed 是刻意的，另一個方向是把「剛好翻到的那一頁」當成最後一頁回報。

### 七、安全測試套件和第二個題目沒有做，這是刻意砍的

- **安全套件**：現在存在的是出口防護、robots 執行、拒絕分類法，全部都是承重的、有測試的。**不存在的**是安全測試題組和注入偵測器，所以注入偵測是一個宣告了但沒有程式路徑到得了的狀態，`/coverage` 頁直接這樣講。
- **第二個題目（SEC 10-K 抽取）沒有做。** 作業要求至少完成一項。我們留下的是一份完整、凍結的介面契約——解析規則、修訂順序、上限行為、雜湊——**而契約後面什麼都沒有**。在只剩兩天的時候，替一個不會存在的產品寫一份完整規格，是從那個會存在的產品身上直接減去。我們把它標成「設計完成、刻意未實作」，因為那份設計是真的工作，假裝不是才是反效果。

### 八、我們在自己的檢查機制裡找到二十個缺陷，修好十七個

一個核心宣稱是「我們的檢查是真的」的系統，必須預期那些檢查本身會出錯。二十個分成三族：

- **十個是同一個物種：一個回報了巧合的檢查。** 從來沒被評估過卻記成「已滿足」的約束；由別的程序的副作用順便滿足的前置條件；沒有東西可比對時回報「通過」的空分支；把缺陷編碼成需求的測試（修掉缺陷反而弄壞測試）。
- **兩個是它的反面：根本沒有檢查。**
- **八個是第三族：我們用自己的話描述自己的頁面，而沒有任何東西在檢查那些話還成不成立。** 這一族最大，也最晚浮現——因為讀 repository 找不到其中任何一個，只有實際操作部署才會撞到。

**兩個最值得看的實例：**

**（一）一道硬性閘門的成敗，取決於一個變數是在哪一瞬間被讀的。** 同一組輸入，前一輪計分通過、下一輪失敗。更值得看的是**第一次的修法錯在前提**：我們假設某個維基百科條目有 HTTP 重導向，實際用瀏覽器量過才發現它回 200、完全沒有重導向，是網站自己的腳本在大約兩秒後改掉網址列的。照第一次的修法，會把一個間歇性的失敗變成一個穩定的失敗。**一個前提沒有被量過的修法不是修法。**

**（二）執行詳情頁連續三天回 500，橫跨全部三輪計分**——就是這份指南叫你點的那一頁。加入自我維護記憶體時，模板多了一段要讀「這個版本有沒有記憶體」，卻沒把那個資訊傳給那一頁；模板引擎對缺漏變數是沉默的，所以其他頁面正常、測試全綠——因為**從來沒有任何測試打開過這一頁**。發現它的方式，是送審當天有人做了評審會第一個做的事：點開一筆執行。它的另一半隔天才浮出來：補的測試證明那一頁**打得開**，卻沒有看著它**動**——即時進度串流斷掉時沒有後備，頁面會停在最後一行繼續轉，而那筆執行其實 13 秒前就成功了。**我們自己的介面，對我們自己的執行狀態，給了一個看起來合理而錯誤的說法。** 現在斷線會**明講**「即時更新已關閉，改為每三秒輪詢」——**無聲地降級只是把同一個缺陷換一件安靜的外衣。**

**三個沒修，理由都一樣**：它們是在建置凍結之後才發現的，修它們會讓部署的版本在「計分結果有報導過的行為」上和計分的版本不一致。**我們選擇讓程式碼難看，讓兩輪計分描述同一個版本。**

### 九、送審前最後一次獨立審查，又找到十一個，其中八個是同一族

我們在送審前請了一個獨立的審查者，只用瀏覽器、不讀任何產品程式碼，照這份指南從頭操作一遍。**他找到十一個這份清單上沒有的問題，其中八個是「文件說了一件頁面上不成立的事」**——上面第三族的第四到第十一個實例。

最難堪的是這一個：上一節說第三族的三個「都已修」，其中一個的修法是「示範用標記指認，不要用位置」。**審查者去數了：整張表格 0 列帶那個標記。** 因為那張表同一段任務只留最新一筆，任何人重跑示範任務都會把示範列擠掉。**我們修好了一句過期的話，換上另一句過期的話，而且一樣沒有東西在檢查它。**

他也推翻了我們自己寫下的兩個結論：我們說中文任務「能力面沒有做」，他實測拿到 `T-DECLARED` + 通過驗證；我們說「不乾淨的安靜結果」徽章在部署上一個實例都找不到，他找到了。**兩個都是朝對我們不利的方向過期**——我們把自己講得比實際差。

這一節本身就是這個提交在講的那件事：**一個看起來合理而錯誤的說法，比一次大聲的失敗嚴重得多。** 我們把這條標準嚴格地套在自己的執行結果上，卻沒有套在自己的操作手冊上。上面那十一個裡，只要是文字能修的都已經修進這份指南，剩下要動到頁面的列在最後一段。

**要動到頁面的那五個現在也修完了**，列在上面表格的第 16 到 20 筆：首頁的標記與擷取日期（改成用旗標選那幾列，不是用「夠新」）、`GET /api/runs`（寫出來了，回完整清單並在截斷時明講）、`/coverage` 的兩句自述（改成從 store 的 `persistent` 旗標渲染，現在說的是「跨部署累計」）、L-1 補救版的失敗原因（改成實測的 `verification_mismatch`，而且那支可執行檢查現在會比對 failure class，不再只比對 terminal status）、以及執行詳情頁只渲染否定半邊的徽章。**五個都是描述錯了，不是機制錯了**——但那正是我們說最嚴重的那一種，所以它們留在這裡，連同「怎麼修的」一起。

修法的共通規則只有一條，值得單獨寫出來：**測試要拿渲染出來的頁面去比對程式碼推導出來的值，不能比對那句話本身。** 前三個之所以能在一次專門在找它們的審查裡活下來，就是因為附近的測試只釘住了散文。
